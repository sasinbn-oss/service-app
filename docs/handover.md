# ส่งมอบโปรเจกต์ให้คนอื่นทำต่อ

เอกสารนี้สำหรับ**เจ้าของโปรเจกต์** ที่จะส่งงานให้คนอื่นพัฒนาต่อ
ไล่ตามลำดับนี้ได้เลย ไม่ต้องรู้เรื่องเทคนิคมาก

ระบบนี้มีสี่ส่วนที่ต้องส่งมอบ และ **แต่ละส่วนอยู่คนละบัญชี**:

| ส่วน | อยู่ที่ | มีอะไรอยู่ |
|---|---|---|
| โค้ด | GitHub | โค้ดทั้งหมด ไม่มีข้อมูลสักแถว |
| เซิร์ฟเวอร์ + เว็บ | Render | ไม่มีข้อมูล แค่รันโค้ด |
| ฐานข้อมูล | Supabase | **ข้อมูลทั้งบริษัท** |
| ไฟล์รูป/วิดีโอ | Supabase Storage | **รูปหน้างาน ใบเสนอราคา บิล** |

สองแถวล่างคือของจริงที่เสียหายแล้วเสียหายเลย ที่เหลือสร้างใหม่ได้

## เลือกก่อนว่าจะส่งแบบไหน

### แบบ ก — ให้เขาเข้ามาช่วยในระบบเดิม (เร็วที่สุด ถอนคืนได้)

เชิญเขาเข้าบัญชีที่มีอยู่ ไม่ต้องย้ายอะไรเลย พี่ยังเป็นเจ้าของทุกอย่าง
และถอนสิทธิ์คืนได้ทุกเมื่อ

**เหมาะเมื่อ** จ้างทำบางส่วน หรือยังไม่แน่ใจว่าจะร่วมงานกันยาวแค่ไหน

### แบบ ข — ให้เขาตั้งระบบของตัวเองขนานไป (ปลอดภัยที่สุด)

เขา clone โค้ดไปตั้ง Render + Supabase ของตัวเอง **ไม่แตะข้อมูลจริงเลย**
ทำเสร็จแล้วส่งโค้ดกลับมาให้พี่ deploy เอง

**เหมาะเมื่อ** ยังไม่ไว้ใจเต็มที่ หรืองานที่ให้ทำไม่จำเป็นต้องใช้ข้อมูลจริง
— ซึ่งเป็นกรณีส่วนใหญ่ การพัฒนาฟีเจอร์ใหม่ไม่ต้องใช้ข้อมูลจริง

### แบบ ค — ย้ายทั้งหมดไปเป็นของเขา

โอนทุกบัญชีให้ **พี่จะไม่เหลือสิทธิ์อะไรเลย** ทำเมื่อเลิกดูแลเองจริง ๆ เท่านั้น
ขั้นตอนอยู่ท้ายเอกสาร

## แบบ ก — เชิญเข้าระบบเดิม

### 1. โค้ด

GitHub → repo → **Settings → Collaborators → Add people** ใส่ username ของเขา

### 2. เซิร์ฟเวอร์

Render → **Workspace Settings → Members → Invite** · ให้สิทธิ์ต่ำสุดที่พอทำงาน

### 3. ฐานข้อมูล — ตรงนี้ต้องคิดก่อน

**อย่าเพิ่งส่ง `DATABASE_URL` ของจริงให้** ถามตัวเองก่อนว่างานที่ให้ทำ
จำเป็นต้องใช้ข้อมูลจริงไหม ส่วนใหญ่ไม่จำเป็น

| เขาต้องการอะไร | ให้แบบไหน |
|---|---|
| แค่พัฒนาฟีเจอร์ | **ไม่ต้องให้เลย** — ให้เขาสร้างโปรเจกต์ Supabase ฟรีของตัวเอง |
| ดูข้อมูลจริงเพื่อหาสาเหตุบั๊ก | สร้าง user **อ่านอย่างเดียว** ให้ (ดูหัวข้อถัดไป) |
| ต้องแก้ข้อมูลจริง | ให้ `DATABASE_URL` เต็ม — **และสำรองข้อมูลก่อน** |

### 4. ก่อนให้สิทธิ์ ทำสองอย่างนี้เสมอ

1. **กดสำรองข้อมูลหนึ่งรอบ** ที่ Supabase → Database → Backups
   จะได้มีจุดกลับที่รู้เวลาแน่นอน
2. **ดูว่าเปิด Point in time recovery ไว้หรือยัง** (Settings → Add-ons)
   ถ้ายัง เสียหายแล้วย้อนได้แค่ backup รอบล่าสุด ซึ่งอาจห่างถึง 24 ชั่วโมง

## สร้าง user อ่านอย่างเดียว

ปลอดภัยกว่าให้ `DATABASE_URL` เต็มมาก — เขาเห็นข้อมูลจริงได้ แต่ลบหรือแก้ไม่ได้
ต่อให้พิมพ์คำสั่งผิดก็ไม่มีอะไรหาย

Supabase → **SQL Editor** → รัน (เปลี่ยนรหัสผ่านเป็นของตัวเอง):

```sql
create role dev_readonly with login password 'ตั้งรหัสผ่านตรงนี้';
grant connect on database postgres to dev_readonly;
grant usage on schema public to dev_readonly;
grant select on all tables in schema public to dev_readonly;
-- ตารางที่สร้างทีหลังก็ให้อ่านได้ด้วย ไม่ต้องมาสั่งซ้ำ
alter default privileges in schema public grant select on tables to dev_readonly;
```

แล้วส่ง connection string ที่เปลี่ยน username กับรหัสผ่านเป็นของ `dev_readonly` ให้เขา

ทดสอบกับฐานข้อมูลจริงแล้วว่าได้ผลตามนี้:

| สั่งอะไร | ผล |
|---|---|
| `select` ข้อมูลสาขา | ได้ครบ 1,204 แถว |
| `delete from "WorkOrder"` | `permission denied for table WorkOrder` |
| `drop table` | `must be owner of table` |
| `drop schema public` (คือสิ่งที่ `migrate reset` ทำ) | `must be owner of schema public` |

เลิกให้สิทธิ์เมื่อไหร่ รันสองบรรทัดนี้:

```sql
drop owned by dev_readonly;
drop role dev_readonly;
```

## สิ่งที่ต้องส่งให้เขาเสมอ

```
1. ลิงก์ repo
2. บอกให้อ่าน README.md หัวข้อ "เริ่มพัฒนาต่อ" กับไฟล์ CLAUDE.md ก่อน
3. บอกว่าให้รัน  bash tests/run-all.sh  ให้ผ่าน 61 ข้อก่อนเริ่มแก้
```

ถ้าเขาใช้ Claude พัฒนาเหมือนกัน บอกแค่นี้พอ — `CLAUDE.md` ถูกอ่านอัตโนมัติ
ทุกครั้งที่เปิดโปรเจกต์ และเก็บกับดักที่เคยเสียเวลาไปแล้วไว้ครบ

## สิ่งที่ห้ามส่งทางแชตหรืออีเมล

ส่งผ่านโปรแกรมจัดการรหัสผ่าน หรือบอกปากเปล่า — **ห้าม commit ลง repo เด็ดขาด**

| ค่า | ถ้าหลุด |
|---|---|
| `DATABASE_URL` / `DIRECT_URL` ของจริง | อ่านและลบข้อมูลทั้งบริษัทได้ |
| `STORAGE_*` | รูปในร้านลูกค้า ใบเสนอราคาและบิลที่มีราคาจริง |
| `JWT_SECRET` | ปลอมตัวเป็นแอดมินได้ |

## แบบ ค — ย้ายทั้งหมดไปเป็นของเขา

ทำตามลำดับนี้ ห้ามสลับ:

1. **สำรองข้อมูล** ที่ Supabase และดาวน์โหลดเก็บไว้เอง
2. **ให้เขาตั้งระบบใหม่ชี้ฐานข้อมูลเดิมก่อน** ตามหัวข้อ
   "รันสองชุดพร้อมกันบนฐานข้อมูลเดียว" ใน README — ยังไม่ต้องย้ายข้อมูล
3. **ทดสอบระบบใหม่ให้ครบ** เปิดใบงาน แนบรูป ปิดงาน ดูรายงาน
4. **ย้ายคนไปใช้ตัวใหม่** แล้วดูสักสองสามวันว่าไม่มีปัญหา
5. **ค่อยย้ายฐานข้อมูลกับไฟล์** ขั้นตอนอยู่ใน `docs/migrate-singapore.md`
   (วิธีขนข้อมูลเหมือนกัน ต่างแค่ปลายทาง)
6. **โอนบัญชี** GitHub (Settings → Transfer ownership) · Render · Supabase
7. **ปิดระบบเก่า** หลังจากมั่นใจแล้วเท่านั้น

**เก็บไฟล์สำรองจากข้อ 1 ไว้เองเสมอ** แม้โอนทุกอย่างไปแล้ว
มันคือข้อมูลของบริษัท ไม่ใช่ของคนที่มาทำระบบ
