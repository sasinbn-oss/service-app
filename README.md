# Service App

แอปสำหรับงานบริการภาคสนาม ประกอบด้วย 9 ฟีเจอร์หลัก:

1. **คู่มือแก้ปัญหา (Troubleshooting guide)** — สองแบบ: ผังวินิจฉัยแบบกดตอบใช่/ไม่ทีละขั้นพร้อมแผนผังวงจร (นำเข้าจาก Excel ของผู้ผลิต) และคู่มือแบบข้อความที่แอดมินเขียนเอง
2. **รายการอะไหล่ (Spare part list)** — ค้นหาจากชื่อ/รหัส/ยี่ห้อ แสดงรหัสสินค้า ยี่ห้อ และรูปภาพ
3. **รายงานตัวเข้าสาขา** — ยืนยันตำแหน่งด้วย GPS เทียบกับพิกัดสาขา
4. **บันทึกข้อมูลการทำงาน** — ลงงานที่ทำในแต่ละวัน
5. **ลงทะเบียนใช้รถ** — เช็คอิน/เช็คเอาท์การใช้รถ พร้อมบันทึกเลขไมล์
6. **เบิกของใช้สิ้นเปลือง** — พนักงานขอเบิก หัวหน้าอนุมัติ ระบบตัดสต็อกอัตโนมัติ
7. **ติดตามเครื่องเสีย** — อัปโหลดไฟล์รายงานวันละ 2 ครั้ง แยกเครื่องดับกับสาขาสัญญาณหาย นับเวลา SLA ให้อัตโนมัติ และกรอกอาการกับสถานะการดำเนินการของแต่ละเคสได้
8. **ใบงานซ่อม** — เปิดใบงานจากกระดานติดตามเครื่องเสียหรือเปิดเอง มอบหมายช่าง และให้ช่างปิดงานพร้อมบันทึกผลและอะไหล่ที่ใช้
9. **เอกสารขอโอนสินค้า** — กรอกคลังต้นทาง/ปลายทางและรายการอะไหล่ ได้ไฟล์ Word หรือ PDF ตามแบบฟอร์มบริษัท

## บัญชีผู้ใช้

**แอดมินสร้างบัญชีให้ทุกคน ผู้ใช้สมัครเองไม่ได้** (เมนู **Admin → สิทธิ์ผู้ใช้**)

1. แอดมินกด **เพิ่มบัญชีผู้ใช้** — ตั้งชื่อผู้ใช้ (รหัสพนักงาน) ชื่อ สิทธิ์ ภาค และ**รหัสตั้งต้น**
2. บอกชื่อผู้ใช้กับรหัสตั้งต้นให้เจ้าของบัญชี
3. เจ้าของบัญชีเข้าระบบครั้งแรก → **ถูกบังคับให้ตั้งรหัสของตัวเองก่อน** ทำอย่างอื่นไม่ได้
4. ตั้งเสร็จเข้าใช้งานได้ทันที ไม่ต้องล็อกอินซ้ำ

**ลืมรหัส** — แอดมินกด **ตั้งรหัสผ่านใหม่ให้** ที่การ์ดของคนนั้น
รหัสใหม่ก็ถูกบังคับให้เปลี่ยนอีกครั้งเหมือนกัน เพราะเป็นรหัสที่แอดมินรู้

**เปลี่ยนรหัสเอง** — เมนู **เปลี่ยนรหัสผ่าน** ในหน้าหลัก ใช้ได้ทุกคนทุกเวลา

### การบังคับเปลี่ยนรหัสกันถึงชั้น API

บัญชีที่ยังใช้รหัสตั้งต้นได้โทเคนที่มีธง `mustChangePassword` ติดอยู่
ทุก endpoint นอกจาก `/auth/change-password` กับ `/auth/me` ตอบ **423** กลับไป

กันที่ middleware ไม่ใช่แค่ซ่อนเมนู เพราะหน้าจอที่ซ่อนไว้ยังเรียก API ตรงๆ ได้
ธงอยู่ในโทเคนแทนการอ่านฐานข้อมูลทุก request — พอเปลี่ยนรหัสเสร็จ ระบบออกโทเคนใหม่
ให้ทันที ผู้ใช้จึงไม่ต้องล็อกอินซ้ำ

**รหัสผ่านต้องยาวอย่างน้อย 8 ตัว** และรหัสใหม่ต้องไม่ซ้ำกับรหัสเดิม
(ตั้งซ้ำของเดิมคือไม่ได้เปลี่ยน ซึ่งไม่ได้แก้ปัญหาที่บังคับให้เปลี่ยนตั้งแต่แรก)

**`POST /api/auth/register` เปิดเฉพาะตอนยังไม่มีผู้ใช้ในระบบเลย** ใช้ตั้งแอดมินคนแรก
ตอนติดตั้งครั้งแรก หลังจากนั้นตอบ 403

ระบบมีการล็อกอินและแบ่งสิทธิ์ผู้ใช้ 2 ระดับ: **พนักงาน (EMPLOYEE)** และ **ผู้ดูแลระบบ (ADMIN)**
ผู้ใช้คนแรกที่ลงทะเบียนในระบบจะได้รับสิทธิ์ ADMIN โดยอัตโนมัติ

## Backend

ใช้ PostgreSQL — แนะนำ [Supabase](https://supabase.com) (มี free tier)

```bash
cd backend
cp .env.example .env       # ใส่ค่า DATABASE_URL / DIRECT_URL จาก Supabase และตั้ง JWT_SECRET
npm install
npx prisma migrate dev     # สร้างตารางทั้งหมด
npx prisma db seed         # ใส่ข้อมูลตัวอย่าง
npm run dev                # รันที่ http://localhost:4000
```

ค่าใน `.env` หาได้จาก Supabase → ปุ่ม **Connect** → **Direct** → **Session pooler**

**ใช้ session pooler (พอร์ต 5432) ไม่ใช่ transaction pooler (6543)** ทั้งที่คู่มือทั่วไป
แนะนำ 6543 — เหตุผลและตัวเลขอยู่ในหัวข้อ "เวลากดบันทึกแล้วช้า" ด้านล่าง
(`DIRECT_URL` ใช้ตอนรัน migration ซึ่งต้องไม่วิ่งผ่าน pooler)

### ติดตามเครื่องเสีย (แดชบอร์ด + อัปโหลดไฟล์)

เมนู **ติดตามเครื่องเสีย** ในแท็บหน้าหลัก แยกเป็น 2 แท็บ เพราะเป็นคนละปัญหา คนละคนแก้

| แท็บ | มาจาก | หน่วย | ใครแก้ |
|---|---|---|---|
| **เครื่องดับ** | `offline = false` และ `state = 0` | รายเครื่อง | ช่างซ่อมเครื่อง |
| **สัญญาณหาย** | `offline = true` (หายทั้งสาขา) **หรือดับเกิน 8 เครื่องในสาขาเดียว** | **รายสาขา** | ทีมเน็ตเวิร์ก |

สาขาที่สัญญาณหาย ค่า `state` ของทุกเครื่องเป็นค่าค้างเก่าที่เชื่อไม่ได้ จึงไม่นับเป็นเครื่องดับ
ส่วน `state` ค่าอื่น (1, 4, 6) ข้ามทั้งหมดตามที่ตกลงกับหน้างาน และไม่เก็บคอลัมน์ `version`

**เครื่องดับพร้อมกันเกิน 8 เครื่องในสาขาเดียว ระบบถือว่าสายขาด** แล้วนับเป็นสัญญาณหายทั้งสาขา
แทนที่จะเปิดใบงานช่างสิบกว่าใบ เพราะเครื่องหลายตัวพังพร้อมกันวันเดียวแทบไม่เกิดขึ้นจริง
ที่เจอคือสายสัญญาณขาดหรือไฟดับ ซึ่งเป็นงานทีมเน็ตเวิร์ก ไม่ใช่ช่างซ่อมเครื่อง
หน้าสรุปก่อนบันทึกจะบอกไว้เสมอว่าย้ายสาขาไหนบ้างและแต่ละสาขาดับกี่เครื่อง
ปรับเกณฑ์ได้ด้วย env `MACHINE_OFF_SIGNAL_THRESHOLD`

**กฎนี้ทำงานตอนนำเข้าไฟล์ ไม่ได้ย้อนไปแก้เคสที่เปิดค้างอยู่แล้ว** สาขาที่ค้างอยู่ในแท็บเครื่องดับ
ตั้งแต่ก่อนเพิ่มกฎ จะย้ายไปแท็บสัญญาณหายเมื่ออัปโหลดไฟล์รอบถัดไป ไม่ต้องทำอะไรเพิ่ม

**เวลาที่ค้างมาไม่ถูกรีเซ็ต** ตอนย้าย ระบบยกเวลาเริ่มของเคสเครื่องดับที่เก่าที่สุดในสาขานั้น
มาเป็นเวลาเริ่มของเคสสัญญาณหาย ถ้าเริ่มนับใหม่จากศูนย์ สาขาที่ดับมาสามวันจะกลายเป็นเพิ่งเสีย
SLA กับคะแนนหายเกลี้ยงทั้งที่ปัญหาไม่เคยหาย แค่เปลี่ยนชื่อเรียก

#### คะแนนความรุนแรง

แต่ละเคสสะสมคะแนนตามจำนวนวันที่ค้าง ใช้จัดลำดับว่าควรเข้าไปแก้ที่ไหนก่อน

| ปัญหา | คะแนนต่อวัน |
|---|---|
| เครื่องดับ | **1** |
| สัญญาณหาย | **3** (กระทบทั้งสาขา ไม่ใช่เครื่องเดียว) |

นับเป็น**วันเต็มที่ผ่านไป** วันแรกจึงได้ 0 เกิน 1 วันได้ 1 เกิน 2 วันได้ 2 ไปเรื่อยๆ
เช่น เครื่องดับมา 76 ชม. = 3 วันเต็ม ได้ 3 คะแนน · สาขาสัญญาณหาย 76 ชม. ได้ 9 คะแนน

คะแนนแสดงเป็นคอลัมน์ในตาราง รวมยอดต่อกลุ่มที่หัวข้อกลุ่ม และรวมทั้งหมดที่การ์ดด้านบน
กดหัวคอลัมน์หรือปุ่ม "คะแนน" เพื่อเรียงจากมากไปน้อยได้

##### คะแนนถูกตรึงไว้ทุกรอบอัปโหลด

คะแนนบนแดชบอร์ดคิดสดจากเวลาปัจจุบัน พอเคสปิดไปคะแนนก็หายไปพร้อมกัน
ทุกครั้งที่**กดยืนยันการอัปโหลด** ระบบจึงตรึงคะแนน ณ ตอนนั้นลงตาราง `ScoreSnapshot`
เก็บเป็นราย **สาขา × ชนิดปัญหา** พร้อมจำนวนเคสและจำนวนที่เลย SLA

- เก็บ **ภาค / ทีมช่าง / เจ้าของ / grade ณ ตอนนั้น** ติดไปกับแถวด้วย ไม่ได้อ้างอิงค่าปัจจุบันของสาขา
  ถ้าอัปโหลดทะเบียนสาขาใหม่แล้วสาขาย้ายภาค **รายงานย้อนหลังจะไม่เปลี่ยนตาม**
- ยอดรวมของแต่ละรอบเก็บซ้ำไว้ที่ `MachineImport` (`machineOffScore` `signalLostScore` `totalScore`)
  ดึงกราฟแนวโน้มได้ด้วยคิวรีเดียวโดยไม่ต้องรวมจาก `ScoreSnapshot`
- **โหมดตรวจสอบไม่เขียน snapshot** เขียนเฉพาะตอน `mode=commit`
- รอบที่อัปโหลดไปก่อนมีฟีเจอร์นี้จะมี `totalScore` เป็น 0 และไม่มีแถว `ScoreSnapshot`
  จึงไม่โผล่ในกราฟย้อนหลัง (ไม่ใช่คะแนนศูนย์จริง แต่คือไม่มีข้อมูล)

อ่านย้อนหลังผ่าน `GET /api/machines/score-history` จัดกลุ่มได้ตามภาค ทีมช่าง หรือเจ้าของ

#### SLA — เวลานับยังไง

ไฟล์ export บอกแค่ว่า *ตอนนี้* ใครมีปัญหา ไม่ได้บอกว่าเริ่มเมื่อไหร่ ระบบจึงจำเอง

```
อัปโหลดเช้า   เจอ C0006/W2 ครั้งแรก  → เปิดเคส เริ่มจับเวลา
อัปโหลดบ่าย   ยังเจอ                → ยังไม่แก้ นับต่อ
พรุ่งนี้เช้า  ยังเจอ                → นับต่อ
พรุ่งนี้บ่าย  ไม่เจอแล้ว            → ซ่อมเสร็จ ปิดเคส บันทึกว่าใช้เวลาไปเท่าไหร่
```

- **เกิน 72 ชม. = เลย SLA** ปรับได้ด้วย env `MACHINE_SLA_HOURS` โดยไม่ต้องแก้โค้ด
- เคสที่ปิดแล้วเก็บเป็นประวัติไว้ (ตาราง `Outage`) ใช้ทำรายงานย้อนหลังได้
- **ความละเอียดของเวลาขึ้นกับรอบอัปโหลด** อัปโหลดวันละ 2 ครั้ง = รู้ผลภายในครึ่งวัน

##### วันที่ของรอบนั้นมาจากไฟล์ ไม่ใช่เวลาที่กดอัปโหลด

ทั้งเวลาเริ่มเคส เวลาปิดเคส SLA และคะแนน อ้างอิงเวลาที่ไฟล์ถูก export
ไม่ใช่เวลาที่คนกดอัปโหลด — export ตอนเช้าแล้วเพิ่งมาอัปโหลดตอนเย็น
หรือลืมไปสองวันแล้วค่อยอัป เวลาที่นับได้ก็ยังเป็นเวลาจริงของข้อมูล

หาวันที่ตามลำดับนี้ อันไหนเจอก่อนใช้อันนั้น

| ลำดับ | ที่มา | ตัวอย่าง |
|---|---|---|
| 1 | ค่าที่ส่งมากับคำขอ (`snapshotAt`) | กรอกเองเมื่อจำเป็น |
| 2 | คอลัมน์ `recorded_at` ในไฟล์ | `2026-08-19 13:30:22` |
| 3 | วันเวลาในชื่อไฟล์ | `machine_offline_20260819_133022.xlsx` |
| 4 | เวลาที่อัปโหลด | ใช้เมื่อไม่มีวันที่ที่ไหนเลย |

ชื่อไฟล์ที่มีแต่วันไม่มีเวลา (`..._20260813.xlsx`) ถือเป็น **เที่ยงวัน** ไม่ใช่เที่ยงคืน
เพราะไฟล์ถูก export ระหว่างวันทำงาน ถ้าใช้เที่ยงคืน SLA จะเดินเกินจริงไปครึ่งวัน

วันเวลาในไฟล์และในชื่อไฟล์อ่านเป็น**เวลาไทย**ทั้งคู่ ไม่ใช่ UTC

หน้าตรวจสอบก่อนบันทึกแสดง **วันที่ของข้อมูล** พร้อมบอกว่าเอามาจากไหน
ถ้าไฟล์เก่ากว่ารอบล่าสุดที่เคยอัปไว้ จะขึ้นเตือนให้ตรวจก่อนกดยืนยัน
เพราะการอัปไฟล์ย้อนหลังจะทำให้ SLA และคะแนนเพี้ยนแบบที่มองไม่เห็น

#### อัปโหลดไฟล์

แอดมินเข้าเมนู **ติดตามเครื่องเสีย → อัปโหลดไฟล์** (ทำได้จากคอมพิวเตอร์เท่านั้น)
เลือกไฟล์ `.xlsx` แล้วระบบจะแสดงสรุปก่อน **ยังไม่บันทึกอะไรจนกว่าจะกดยืนยัน**

คอลัมน์ที่ต้องมี: `crm_code` `num` `state` `offline` (เสริม: `name` `brand_type` `machine_type` `machine_brand`)

**⚠ เครื่องที่ไม่อยู่ในไฟล์จะถือว่าซ่อมเสร็จแล้ว** เพราะไฟล์นี้ export เฉพาะเครื่องที่มีปัญหา
หน้าสรุปจึงบอกจำนวน "เคสที่จะปิด" ไว้เสมอ — ถ้าสูงผิดปกติแปลว่าไฟล์อาจ export มาไม่ครบ
ให้ตรวจก่อนกดยืนยัน

**แถวซ้ำถูกตัดอัตโนมัติ** ไฟล์จริงเคยมีสาขาหนึ่งซ้ำ 112 รอบต่อเครื่อง ทำให้ยอดผิดเกือบเท่าตัว
(1,455 แถว → 1,011 แถว · เครื่องดับ 973 → 482) ระบบจะแจ้งจำนวนที่ตัดออกไว้ในหน้าสรุป

**ความเร็ว** — การเขียนสาขาและเครื่องทั้งหมดใช้คำสั่ง SQL แบบ `unnest` ชุดเดียว
ไม่ใช่ upsert ทีละแถว ไฟล์ 1,011 แถวจึงใช้การคุยกับฐานข้อมูลแค่ 4 รอบ แทนที่จะเป็น 1,331 รอบ
สำคัญมากเมื่อฐานข้อมูลอยู่คนละที่กับเซิร์ฟเวอร์ (เช่น Supabase) เพราะแต่ละรอบมีค่า latency ของตัวเอง
ถ้าวันหลังแก้ไฟล์นี้ อย่าเปลี่ยนกลับไปเป็น upsert ในลูป

#### ไฟล์ที่ 2: ทะเบียนสาขา (ภาค / ทีมช่าง)

แท็บ **ทะเบียนสาขา** ในหน้าอัปโหลดเดียวกัน อัปเดตราวสัปดาห์ละครั้งเมื่อมีการเปลี่ยนแปลง

| คอลัมน์ในไฟล์ | เก็บเป็น | ใช้ทำอะไร |
|---|---|---|
| `Row Labels` หรือ `code` | `Branch.code` | รหัสสาขา |
| `ชื่อสาขา` | `Branch.name` | ตั้งเฉพาะตอนสร้างใหม่ |
| `ผจก.ภาค` | `Branch.region` | ภาคที่หัวหน้าภาคดูแล |
| `ผู้ดูแล CM` | `Branch.zone` | ทีมที่รับงาน CM ของสาขานี้ |
| `ผู้ดูแล PM` | `Branch.pmTeam` | ทีมที่รับงาน PM — ว่างได้ |
| `วันส่งมอบร้าน` | `Branch.openedAt` | วันเปิดร้าน ใช้คู่กับประกัน |
| `GPS` | `latitude` / `longitude` | ให้ช่างรายงานตัวด้วย GPS ได้ |

ใส่ `grade` กับ `วันหมดประกัน` เพิ่มได้ถ้ามี — ไม่มีก็ไม่ลบค่าเดิมทิ้ง

**ชื่อคอลัมน์รับได้หลายแบบ** เช่น `code` / `รหัสสาขา` / `Row Labels` และ `ผจกภาค` / `ผจก.ภาค`
เพราะไฟล์จริงแต่ละรอบไม่ได้ใช้หัวตารางเดียวกัน — ไฟล์ที่ทำจาก PivotTable ตั้งหัวคอลัมน์แรก
ว่า "Row Labels" ให้เอง การไปไล่แก้หัวตารางทุกครั้งก่ออัปโหลดคืองานที่จะถูกลืม

**พิกัดอ่านจากช่องเดียวแบบ `8.07475, 98.995222`** (ก๊อปจาก Google Maps มาตรง ๆ)
ค่าที่อยู่นอกประเทศไทยถือว่าผิดและถูกข้าม ไม่ใช่แค่แปลก — สาขาที่พิกัดเพี้ยนทำให้ช่าง
รายงานตัวไม่ผ่านทั้งที่ยืนอยู่หน้าร้าน พิกัดในไฟล์ทับของเดิมได้ แต่ไฟล์ที่ไม่มีพิกัด
จะไม่ล้างของเดิมทิ้ง

**วันที่รับทั้ง `26/2/2021` และวันที่จริงของ Excel** ในไฟล์เดียวกัน (ไฟล์จริงมีทั้งสองแบบปนกัน)
และแปลง พ.ศ. กลับเป็น ค.ศ. ให้ถ้าปีมากกว่า 2400

- **ไม่แตะสถานะเครื่องหรือเคสที่เปิดค้างอยู่เลย** อัปเดตเฉพาะข้อมูลทะเบียนสาขา
- สาขาที่มีในไฟล์แต่ยังไม่มีในระบบจะถูกสร้างให้ (ทะเบียนมีทุกสาขา ส่วนรายงานเครื่องมีเฉพาะสาขาที่มีปัญหา)
- **ชื่อสาขาไม่ถูกเขียนทับ** ตั้งเฉพาะตอนสร้างใหม่ เพราะชื่อในทะเบียนมีรหัสภายในต่อท้าย
  (`ถนนอุตรกิจ กระบี่ 00031 KBI009 C0006`) ส่วนชื่อจากรายงานเครื่องสะอาดกว่าและเป็นชื่อที่ขึ้นบนแดชบอร์ด
- สาขาที่อยู่ในระบบแต่ไม่มีในไฟล์ **ไม่ถูกแตะ** และรายงานจำนวนไว้ในหน้าสรุป
- รหัสซ้ำที่ข้อมูลไม่ตรงกันจะถูกแจ้งเป็นชื่อรหัสให้ไปแก้ที่ต้นทาง

หน้าสรุปก่อนบันทึกบอก: สาขาใหม่ / สาขาที่ภาคหรือทีมช่างจะเปลี่ยน (พร้อมตัวอย่าง ก่อน → หลัง) /
สาขาที่เหมือนเดิม / จำนวนสาขาต่อภาค ต่อทีม CM และต่อทีม PM / สาขาที่จะได้พิกัดเพิ่ม /
สาขาที่ไม่ได้ระบุทีม PM

**เตือนเมื่อชื่อภาคสะกดไม่ตรงกัน** เช่น `เหนือ-อีสาน` กับ `เหนือ อีสาน` ซึ่งระบบถือเป็นคนละภาค
ผลคือหัวหน้าภาคที่ตั้งไว้ภาคหนึ่งจะมองไม่เห็นสาขาที่สะกดอีกแบบเลย ระบบไม่แก้ให้เงียบ ๆ
เพราะเดาแทนคนไม่ได้ว่าอันไหนถูก แต่ต้องเห็นก่อนกดบันทึก

เมื่อมีข้อมูลแล้ว แดชบอร์ดจัดกลุ่มตาม **ภาค** เป็นค่าเริ่มต้น สลับเป็นทีมช่างหรือเจ้าของได้
สาขาที่ยังไม่มีภาคจะขึ้นกลุ่ม "ยังไม่ระบุภาค" ไม่ใช่ซ่อนหาย

ตัวกรองเรียงตามลำดับชั้นจริง — **เจ้าของ (COCO/DODO) ก่อน แล้วค่อยเจาะลงภาค**
แถบภาคอยู่ใต้แถบเจ้าของและแสดงจำนวนเคสของแต่ละภาคกำกับไว้ เปลี่ยนเจ้าของแล้วภาคที่เลือกไว้
จะถูกล้างอัตโนมัติ เพราะภาคที่เลือกไว้อาจไม่มีเคสอยู่ใต้เจ้าของใหม่เลย
มีปุ่ม "ยังไม่ระบุภาค" ให้ดึงเฉพาะสาขาที่ทะเบียนยังไม่ครบด้วย

การ์ดด้านบนบอกทั้งจำนวนเครื่องและ**จำนวนสาขาที่มีปัญหา** เพราะ "ดับ 40 เครื่อง" ที่กระจายอยู่
40 สาขา กับที่กระจุกอยู่ 3 สาขา เป็นคนละปัญหาและใช้คนละวิธีแก้

#### อาการและสถานะการดำเนินการ

ไฟล์ export บอกได้แค่ว่าเครื่องดับ ไม่ได้บอกว่าเสียเพราะอะไรและตอนนี้ติดอยู่ที่ขั้นไหน
สองอย่างนี้จึงให้คนกรอกเอง — **แตะที่รายการไหนก็ได้ในแดชบอร์ด** จะขึ้นฟอร์มให้กรอก

| ช่อง | ใส่อะไร |
|---|---|
| **อาการที่พบ** | ข้อความอิสระ เช่น "บอร์ดควบคุมไม่จ่ายไฟ" (ไม่เกิน 500 ตัวอักษร) |
| **สถานะการดำเนินการ** | เลือกจาก รออะไหล่ / รอช่างเข้าแก้ไข / รอลูกค้าจ่ายเงิน / รอลูกค้าแจ้งซ่อม |

เลือกสถานะ **รอช่างเข้าแก้ไข** แล้วจะมีช่องให้ใส่วันที่ช่างนัดเข้า (มีปุ่มลัด วันนี้ / พรุ่งนี้ / อีก 7 วัน)
วันนัดขึ้นเป็นป้ายสีฟ้าในแถว จะได้เห็นว่าเคสไหนนัดไว้แล้วและเคสไหนยังลอยอยู่

เลือกสถานะ **รออะไหล่** แล้วจะมีช่องให้ระบุด้วยว่ารออะไหล่ตัวไหน เลือกจากรายการอะไหล่ในระบบ
(ค้นด้วยรหัสหรือชื่อ) ใส่จำนวนได้ และใส่ได้หลายตัวต่อหนึ่งเคส

ที่ไม่ให้พิมพ์รหัสเองเพราะรหัสที่พิมพ์มือจะสะกดไม่ตรงกัน แล้วจะรวมยอดไม่ได้ว่าตอนนี้
ทั้งประเทศค้างอะไหล่ตัวไหนอยู่กี่ตัว — พอผูกกับรหัสจริงแล้วทำได้สองอย่าง:
พิมพ์รหัสอะไหล่ในช่องค้นหาของแดชบอร์ดเพื่อดูว่ามีเคสไหนรอตัวนี้อยู่บ้าง
และเรียก `GET /api/machines/waiting-parts` เพื่อดูยอดรวมทุกตัวเรียงจากมากไปน้อย

> ถ้าอะไหล่ที่รอยังไม่มีในระบบ ให้แอดมินเพิ่มที่เมนู **รายการอะไหล่** ก่อน
> หรือพิมพ์ไว้ในช่องอาการไปพลางๆ ได้

- **ทุกคนที่ล็อกอินแก้ได้** ไม่จำกัดเฉพาะแอดมิน เพราะช่างที่ไปหน้างานเป็นคนรู้อาการ

#### ประวัติการกรอก

ทุกครั้งที่กดบันทึกจะถูกเก็บเป็นแถวใหม่ในตาราง `OutageNoteLog` ไม่ได้เขียนทับของเดิม
เก็บว่าใครกด เมื่อไหร่ และตอนนั้นกรอกอะไรไว้ (อาการ สถานะ อะไหล่ วันนัด)

- **ในฟอร์มของเคส** ขึ้นไทม์ไลน์ของเคสนั้น เก่าสุดอยู่บน จะได้ไล่ได้ว่าเรื่องเดินมายังไง
- **ปุ่ม "ประวัติการกรอก"** มุมบนขวาของแดชบอร์ด รวมทุกเคส ล่าสุด 100 ครั้ง ใหม่สุดอยู่บน
  ตอบว่าวันนี้มีใครมาอัปเดตอะไรบ้างโดยไม่ต้องเปิดทีละเคส

เก็บเป็น snapshot ของค่าหลังบันทึก ไม่ใช่ส่วนต่าง อ่านย้อนหลังแล้วรู้ทันทีว่าตอนนั้น
เคสอยู่ในสภาพไหน โดยไม่ต้องไล่ประกอบจากรายการก่อนหน้า

> เคสที่กรอกไว้ก่อนเพิ่มฟีเจอร์นี้จะไม่มีประวัติย้อนหลัง ฟอร์มจะบอกไว้ว่าใครแก้ล่าสุด
> พร้อมหมายเหตุว่าบันทึกไว้ก่อนระบบเริ่มเก็บประวัติ
- **ผูกกับเคส ไม่ใช่กับเครื่อง** เครื่องเดิมที่ดับรอบใหม่จึงเริ่มจากว่างเสมอ ไม่มีอาการของรอบก่อนติดมา
  ส่วนเคสที่ปิดไปแล้วยังเก็บอาการไว้เป็นประวัติ
- **อัปโหลดไฟล์ทับไม่ลบข้อมูลที่กรอกไว้** เคสที่ยังเปิดอยู่ระบบแค่ต่ออายุ ไม่ได้สร้างใหม่
- แถบ **สถานะ** เหนือตารางใช้กรองได้ รวมถึงปุ่ม "ยังไม่ระบุ" ที่ดึงเฉพาะเคสที่ยังไม่มีใครกรอก
  ซึ่งเป็นกลุ่มที่ต้องตามมากที่สุด

#### หน้าจอปรับตามความกว้าง

หน้าอื่นในแอปเป็นฟอร์มที่ออกแบบมาสำหรับมือถือ จึงถูกจำกัดความกว้างไว้ที่ 820px
ปล่อยให้ยืดเต็มจอคอมจะกลายเป็นแอปมือถือที่ถูกซูมขึ้นมา แต่แดชบอร์ดเป็นตารางข้อมูล
ยิ่งกว้างยิ่งเห็นเยอะ จึงขอความกว้างเป็นรายหน้าผ่าน `useWideLayout()` ใน `components/AppShell.tsx`
ไม่ได้ปลดเพดานทิ้งทั้งแอป

| ความกว้าง | หน้าตา |
|---|---|
| ต่ำกว่า 700px | การ์ดแทนตาราง ทุกอย่างอยู่ในการ์ดเดียวกัน |
| 700–999px | ตาราง อาการกับสถานะอยู่บรรทัดที่สองของแถว |
| 1000px ขึ้นไป | ตัวกรองยุบเหลือ 2 บรรทัด จากเดิม 5 บรรทัด |
| 1258px ขึ้นไป | อาการกับสถานะกลับมาเป็นคอลัมน์ของตัวเอง |
| เพดาน 1600px | กว้างกว่านี้หัวตารางจะห่างจากข้อมูลเกินกวาดตาตาม |

ที่ว่างที่เหลือแบ่งให้ช่องที่ยาวไม่จำกัด คือ **อาการ** ก่อน แล้วค่อย **ชื่อสาขา**
บนจอ 1920 เห็นข้อมูลได้ 10 แถวโดยไม่ต้องเลื่อน จากเดิม 5 แถว

#### ไฟล์ที่ 3: สาขาหรือเครื่องที่ยกเลิก

แท็บ **สาขาที่ยกเลิก** ในหน้าอัปโหลดเดียวกัน ใช้เมื่อมีสาขาปิดหรือถอดเครื่องออก

**ไฟล์เดียวรับได้สองระดับ** ขึ้นกับว่ามีคอลัมน์หมายเลขเครื่องหรือไม่

| แถวในไฟล์ | ความหมาย |
|---|---|
| `code` อย่างเดียว | ยกเลิก**ทั้งสาขา** ปิดเคสของทุกเครื่องในสาขานั้น |
| `code` + `num` | ถอด**เฉพาะเครื่องนั้น** สาขาและเครื่องอื่นยังทำงานปกติ |

คอลัมน์: `code` (หรือ `รหัสสาขา`) จำเป็น · `num` (หรือ `หมายเลขเครื่อง`) ใส่เมื่อถอดรายเครื่อง ·
`ชื่อสาขา` และ `หมายเหตุ` ใส่เพิ่มได้

ถอดรายเครื่องเจอบ่อยกว่าปิดทั้งสาขา — สาขายังเปิดอยู่แต่ยกเครื่องออกไปบางตัว

**ปัญหาที่ไฟล์นี้แก้:** สาขาที่เลิกกิจการไปแล้วยังถูก export ออกมาในรายงานเครื่องทุกรอบ
โดยเครื่องทุกตัวอ่านค่าเป็น `state 0` เพราะไม่มีอะไรส่งสัญญาณกลับมา ระบบจึงเปิดเคสค้างไว้
ตลอดกาล สะสม SLA และคะแนนทั้งที่ไม่มีเครื่องให้ใครไปซ่อม และขึ้นใบงานให้ช่างทุกเช้า

รายงานเครื่องบอกเองไม่ได้ — คอลัมน์ `status` ในไฟล์เป็น `active` ทุกแถวเสมอ

- กดยืนยันแล้วระบบ **ปิดเคสที่ค้างอยู่ทันที** ไม่ต้องรอให้หายจากไฟล์
- **รอบอัปโหลดถัดไปจะข้ามรายการเหล่านี้** หน้าสรุปแยกให้ว่าข้ามเพราะสาขายกเลิกกี่สาขา
  และเพราะเครื่องถูกถอดกี่เครื่อง
- **ไม่ได้ลบทิ้ง** ประวัติเคสเก่ายังอ่านย้อนหลังได้
- **กู้คืนได้ทั้งสองระดับ** เพิ่มคอลัมน์ `action` (หรือ `คำสั่ง`) ใส่ค่า `restore` แล้วอัปโหลดไฟล์เดิมซ้ำ

**คอลัมน์ `status` ในไฟล์ถูกมองข้าม** เพราะวิธีทำไฟล์นี้จริงๆ คือ copy แถวออกมาจาก
ไฟล์รายงานเครื่อง ซึ่งมีคอลัมน์ `status` ติดมาด้วยและอ่านเป็น `active` ทุกแถวเสมอ
ถ้าเอาค่านั้นมาแปลว่าเจตนา ไฟล์ที่ copy มาจะกลายเป็นคำสั่งกู้คืนทั้งไฟล์ คือตรงข้าม
กับที่ตั้งใจ เจตนากู้คืนจึงต้องเขียนในคอลัมน์ `action` ของตัวเองเท่านั้น

**เก็บที่ `Branch.cancelledAt` / `Machine.removedAt` ไม่ใช่ช่อง `status`** เพราะตัวนำเข้ารายงานเครื่อง
เขียนทับ `status` ทุกรอบจากคอลัมน์ในไฟล์ ถ้าใช้ช่องนั้นสถานะยกเลิกจะถูกล้างทิ้ง
ในการอัปโหลดครั้งถัดไป

##### เหตุผลการปิดเคส

`Outage.closeReason` แยก **`REPAIRED`** (หายไปจากไฟล์เอง = ซ่อมเสร็จจริง) ออกจาก
**`BRANCH_CANCELLED`** (สาขายกเลิก) และ **`MACHINE_REMOVED`** (ถอดเครื่องออก) —
สองอย่างหลังคือคนสั่งปิด ไม่ใช่ผลงานของช่าง

จำเป็นเพราะรายงานผู้บริหารคิดเวลาเฉลี่ยที่ใช้ซ่อมจากเคสที่ปิดแล้ว ถ้านับรวมกัน
เครื่องที่ค้างมา 40 วันแล้วสาขาปิด จะถูกนับเป็น "งานซ่อมที่ใช้เวลา 40 วัน"
แล้วค่าเฉลี่ยเพี้ยนถาวรโดยไม่มีใครรู้ — รายงานจึงนับเฉพาะ `REPAIRED`
และแยกจำนวนที่ปิดเพราะสาขายกเลิกไว้ที่ `closedByCancellation`

### ใบงานซ่อม

เมนู **ใบงานซ่อม** — ของที่ช่างถือไปทำ เปิดได้สองทาง

| ทาง | ใช้เมื่อ |
|---|---|
| **จากกระดานติดตามเครื่องเสีย** | ปุ่ม `+ สร้างใบงาน` ท้ายทุกแถว ทั้งแท็บเครื่องดับและแท็บสาขาสัญญาณหาย สาขาและเครื่องมาจากเคสให้เอง |
| **เปิดเอง** | ปุ่ม `+ เพิ่มใบงาน` ในหน้ารายการ สำหรับงานที่ไฟล์ไม่รู้ เช่น ลูกค้าโทรแจ้ง หรืองานติดตั้ง |

#### ใบงานกับเคสบนกระดาน ไม่ใช่อันเดียวกัน

แยกกันโดยตั้งใจ **เคส (`Outage`) คือสภาพของเครื่อง ใบงาน (`WorkOrder`) คือสิ่งที่คนไปทำ**

- เคสเปิดและปิดตามไฟล์ export เท่านั้น คนสั่งปิดเองไม่ได้ เพราะไฟล์คือความจริง
  ว่าเครื่องกลับมาหรือยัง
- ใบงานปิดโดยช่าง เมื่อไปทำแล้ว
- **ปิดใบงานไม่ได้ปิดเคส** ช่างไปเปลี่ยนอะไหล่แล้วเครื่องยังไม่กลับมาก็มี
  ถ้าปิดเคสให้อัตโนมัติ กระดานจะสะอาดทั้งที่ปัญหายังอยู่ ซึ่งเป็นการโกหกที่อันตราย
  หน้าปิดงานจึงเตือนตรงๆ ว่าเครื่องยังขึ้นว่าดับอยู่ในไฟล์รอบล่าสุด
- เคสหนึ่งมีใบงานได้หลายใบ ถ้าช่างต้องเข้าไปหลายรอบ แต่ **เปิดค้างพร้อมกันได้ใบเดียว**
  ไม่งั้นเช้าวันจันทร์จะมีคนเปิดซ้ำ แล้วช่างสองคนขับไปสาขาเดียวกัน
  กระดานจึงแสดงรหัสใบงานที่เปิดค้างอยู่แทนปุ่ม

#### อาการและสถานะกรอกที่ใบงาน

ช่องเดียวกับที่เคยกรอกบนกระดาน (**อาการที่พบ** · **สถานะการดำเนินการ** · **อะไหล่ที่รอ** ·
**วันที่ช่างจะเข้า**) ย้ายมาอยู่ในใบงาน เพราะคนที่รู้คือช่างที่ถือใบงานไป
ไม่ใช่คนที่นั่งดูกระดาน

**กระดานยังแสดงค่าเหล่านี้เหมือนเดิม แต่ดึงมาจากใบงาน** พร้อมบอกว่ามาจากใบไหน (`จาก WO-00042`)

- เคสที่**มีใบงานแล้ว** — แตะบนกระดานจะไม่ให้กรอกซ้ำ แต่ขึ้นปุ่มพาไปแก้ที่ใบงาน
  สองที่ที่แก้ได้พร้อมกันแปลว่าจะมีอันหนึ่งเก่ากว่าเสมอ แล้วไม่มีใครรู้ว่าอันไหน
- เคสที่**ยังไม่มีใบงาน** — กรอกบนกระดานได้ตามเดิม ไม่งั้นเคสส่วนใหญ่จะแก้ไม่ได้เลย
- เปิดใบงานจากเคสที่เคยกรอกไว้แล้ว ค่าเดิมถูกยกมาเป็นค่าตั้งต้น ไม่ได้ทิ้งแล้วเริ่มใหม่

**เก็บสำเนาไว้ที่เคสด้วย** (`Outage.symptom` / `workStatus` / `scheduledVisitAt` / `OutagePart`)
โดยให้ใบงานเป็นฝ่ายเขียน เพราะตัวกรองบนกระดาน รายงานอะไหล่ที่ต้องสั่ง และรายงานรายวัน
อ่านจากเคสอยู่แล้ว ถ้าย้ายไปอยู่ที่ใบงานอย่างเดียวต้องรื้อทั้งหมดนั้น

ประวัติการกรอกของเคสยังต่อเนื่องกับของเดิม โดยมีรหัสใบงานกำกับว่ามาจากใบไหน

##### อะไหล่ที่รอ ≠ อะไหล่ที่ใช้

`WorkOrderPart.kind` แยก **`WAITING`** (รออะไหล่ตัวนี้อยู่ กรอกตอนเปิดงาน)
ออกจาก **`USED`** (ใช้ไปจริง กรอกตอนปิดงาน)

ช่างอาจไปถึงแล้วพบว่าเสียคนละจุด ของที่รอกับของที่ใช้จึงไม่จำเป็นต้องตรงกัน
ถ้าเก็บรวมกันจะแยกไม่ออกว่ายอดที่ต้องสั่งซื้อคือเท่าไหร่

#### สายงาน 5 ขั้น

ใบงานเดินตามสายงานจริง ทีละขั้น ข้ามไม่ได้

| ขั้น | สถานะ | คนทำ | ทำอะไร |
|---|---|---|---|
| 1 | `NEW` รอหัวหน้าภาคระบุอะไหล่ | แอดมิน (เปิดให้) | เปิดใบงาน ใส่อาการและความเร่งด่วน |
| 2 | `NEW` → | หัวหน้าภาค | ตัดสินว่าใช้อะไหล่ไหม แล้วระบุรายการ |
| — | `AWAITING_QUOTE` รอเสนอราคาลูกค้า | แอดมิน | แนบใบเสนอราคา ส่งให้ลูกค้า (เฉพาะงานที่ขายอะไหล่) |
| — | `AWAITING_PAYMENT` รอลูกค้าจ่ายเงิน | แอดมิน | แนบบิลที่ลูกค้าจ่ายแล้ว (เฉพาะงานที่ขายอะไหล่) |
| 3 | `PARTS_REQUESTED` รอแอดมินเช็คอะไหล่ | แอดมิน | เบิกของออกจากคลัง — ระบุคลังและเลขใบเบิกของแต่ละตัว |
| 4 | `PARTS_CHECKED` รอหัวหน้าภาคจ่ายงาน | หัวหน้าภาค | จ่ายงานให้ทีมช่าง แล้วนัดวันเข้า |
| 5 | `ASSIGNED` รอหัวหน้าภาคนัดวัน → `IN_PROGRESS` | ช่าง | เข้าหน้างาน แล้วปิดงาน |

จบที่ `DONE` (หรือ `CANCELLED`)

**ป้ายสถานะเขียนเป็น "รอใคร" ไม่ใช่ "ทำอะไรไปแล้ว"** เพราะคนเปิดหน้ารายการ
อยากรู้ว่าใบไหนค้างที่ตัวเอง

##### เสนอราคาและรับเงิน มาก่อนเบิกอะไหล่

งานที่ต้องขายอะไหล่ให้ลูกค้าแฟรนไชส์ **เก็บเงินให้จบก่อนของออกจากคลัง** ไม่ใช่
เบิกของไปก่อนแล้วค่อยตามเก็บเงิน

เหตุผลคือของที่เบิกออกไปแล้วเอากลับเข้าคลังไม่ได้ง่าย ๆ ถ้าลูกค้าไม่ตกลงราคา —
ใบเบิกถูกตัดไปแล้ว ของอยู่กับช่าง สต็อกขาดไปจริง และคนที่ต้องตามเก็บเงิน
ไม่ใช่คนที่ตัดสินใจเบิก กลับกันถ้ายังไม่เบิก การที่ลูกค้าไม่เอาคือการปิดใบงาน
เฉย ๆ ไม่มีอะไรต้องตามคืน

ระบบตัดสินว่าต้องเสนอราคาไหม**ตั้งแต่หัวหน้าภาคระบุอะไหล่เสร็จ** เพราะเงื่อนไข
ทั้งสามข้อ (สาขาแฟรนไชส์ · ใช้อะไหล่ · หมดประกัน) รู้ครบตั้งแต่ตอนนั้น ไม่ต้อง
รอผลเช็คสต็อก

บนแถบขั้นตอน ใบที่ไม่เข้าเงื่อนไขจะเห็นสองขั้นนี้ขึ้นว่า **ข้าม** ไม่ใช่ขึ้นว่าทำแล้ว —
ต้องทำเครื่องหมายไว้ เพราะตอนนี้สองขั้นนั้นอยู่*ก่อน*ขั้นปัจจุบัน ถ้าไม่ทำ
มันจะดูเหมือนผ่านมาแล้วทั้งที่ไม่เคยทำ

หลังรับเงิน สถานะการดำเนินการเปลี่ยนเป็น **รออะไหล่** ไม่ใช่ค้างที่ "รอลูกค้าจ่ายเงิน"
— ขั้นเบิกอะไหล่ตั้งค่านี้เองเสมอ ไม่ปล่อยให้ค่าของขั้นก่อนค้างมา

##### สิทธิ์

| สิทธิ์ | เห็นอะไร | ทำอะไร |
|---|---|---|
| **ช่าง** (`EMPLOYEE`) | เฉพาะงานของทีมตัวเอง | ปิดงาน หรือส่งกลับ |
| **หัวหน้าภาค** (`SUPERVISOR`) | เฉพาะใบงานของภาคที่ดูแล | ระบุอะไหล่ จ่ายงาน นัดวัน |
| **แอดมิน** (`ADMIN`) | ทุกใบ | ทุกขั้น รวมทำแทนคนอื่น |

หัวหน้าภาคต้องตั้ง **ภาคที่ดูแล** ด้วย (เมนู **Admin → สิทธิ์ผู้ใช้**) ไม่งั้นจะไม่เห็นใบงานใดเลย
ภาคที่เลือกได้มาจากทะเบียนสาขาจริง จะได้ไม่พิมพ์ชื่อภาคผิดจนกรองไม่เจอ

**ช่างต้องตั้งทีมที่สังกัด** ที่เดียวกัน ด้วยเหตุผลเดียวกัน — งานถูกจ่ายให้ทีม
ช่างที่ยังไม่ได้จัดทีมจะเห็นเฉพาะงานเก่าที่เคยจ่ายให้ตัวเองรายคน ซึ่งเป็นพฤติกรรมเดิมพอดี
แอดมินจึงทยอยจัดทีมได้ทีละคนโดยไม่มีใครมองไม่เห็นงานตัวเองระหว่างทาง

**แอดมินทำแทนได้ทุกขั้น แต่ข้ามลำดับไม่ได้** งานด่วนรอหัวหน้าภาคว่างไม่ได้
แต่ถ้าข้ามลำดับได้จะมีใบงานที่จ่ายให้ช่างทั้งที่ยังไม่มีใครเช็คว่ามีอะไหล่หรือเปล่า
ประวัติบันทึกไว้ว่าใครเป็นคนกดจริง

**ปุ่มขึ้นเฉพาะเมื่อถึงคิวของคนที่เปิดดู** คนอื่นเห็นเป็นข้อความว่ากำลังรอใครอยู่ —
ปุ่มที่กดแล้วโดนปฏิเสธคือปุ่มที่ทำให้คนสงสัยว่าตัวเองทำอะไรผิด ทั้งที่แค่ยังไม่ถึงคิว

##### กล่องงาน — ใบไหนถึงคิวของใคร

เมนู **กล่องงานของฉัน** ในหน้าแรก พร้อมตัวเลขบอกว่ามีกี่ใบรออยู่ กดแล้วเปิดรายการ
ใบงานที่กรองไว้ที่ชิป **กล่องงานของฉัน** ให้เลย

| บทบาท | กล่องงานมีอะไร |
|---|---|
| **ช่าง** | `รอช่างนัดวัน` · `รอช่างเข้างาน` ของทีมตัวเอง |
| **หัวหน้าภาค** | `รอหัวหน้าภาคระบุอะไหล่` · `รอหัวหน้าภาคจ่ายงาน` ของภาคที่ดูแล |
| **แอดมิน** | `รอแอดมินเช็คอะไหล่` ทุกภาค |

**กล่องงานไม่ได้เก็บข้อมูลใหม่อะไรเลย** — ใบงานเดินตามสายงานทีละขั้น และแต่ละขั้น
มีเจ้าของขั้นชัดเจนอยู่แล้ว (`WORK_ORDER_STAGE_ACTOR`) กล่องงานคือคำถามเดียวกันกับ
"ตอนนี้ลูกบอลอยู่ที่ใคร" ที่ระบบตอบได้อยู่แล้ว ประกอบกับขอบเขตที่คนนั้นเห็น (ภาค / ทีม)

ทำเป็นตารางแยกว่า "ใบนี้อยู่ในกล่องของใคร" จะกลายเป็นความจริงชุดที่สองที่ต้องคอย
ให้ตรงกับสถานะใบงาน แล้ววันหนึ่งจะไม่ตรง — กล่องมีใบที่ทำไปแล้ว หรือใบที่ถึงคิว
แต่ไม่โผล่ ซึ่งแย่กว่าไม่มีกล่องงานเลย

**แอดมินเห็นเฉพาะขั้นเช็คอะไหล่ในกล่องตัวเอง** ทั้งที่ทำแทนได้ทุกขั้น เพราะกล่องงาน
ตอบว่า "อะไรรอฉันอยู่" ไม่ใช่ "อะไรที่ฉันมีสิทธิ์กด" — ถ้าใส่ทุกใบที่แอดมินแตะได้
กล่องจะเท่ากับรายการทั้งหมด แล้วไม่มีประโยชน์ ส่วนการทำแทนยังทำได้จากรายการรวมเหมือนเดิม

##### ขั้นเสนอราคา — เฉพาะอะไหล่ที่ขายให้ลูกค้าแฟรนไชส์

อะไหล่ที่ใส่ให้สาขาแฟรนไชส์ที่หมดประกันแล้ว เป็นของที่**ขายให้ลูกค้า** ไม่ใช่ของแถม
ต้องเสนอราคาและเก็บเงินก่อนส่งช่างไป ไม่งั้นของออกจากคลังไปแล้วค่อยมาตามเก็บเงิน
ซึ่งเป็นตอนที่ตามยากที่สุด

ใบงานจึงแทรกสองขั้นหลังเช็คอะไหล่ ก่อนจ่ายงาน — **แอดมินทำทั้งคู่** เพราะเป็นงาน
ออฟฟิศ แอดมินเป็นคนรู้ราคาและเป็นคนออกเอกสาร

| ขั้น | ต้องแนบ |
|---|---|
| `AWAITING_QUOTE` รอเสนอราคาลูกค้า | **ใบเสนอราคา** |
| `AWAITING_PAYMENT` รอลูกค้าจ่ายเงิน | **บิลที่ลูกค้าจ่ายแล้ว** |

ต้องแนบเอกสารจริง ไม่ใช่แค่กดว่าทำแล้ว — ใบเสนอราคาคือสิ่งที่ลูกค้าตอบรับ และเป็นตัวที่
ต้องงัดมาดูตอนลูกค้าทักว่าราคาไม่ตรงกับที่ตกลงกันไว้ ส่วนบิลคือเอกสารที่ผูกกับเงินที่เข้ามา
เงินที่ไม่มีเอกสารผูกไว้คือเงินที่กระทบยอดไม่ได้ตอนปิดเดือน

**ผ่านสองขั้นนี้เมื่อครบสามเงื่อนไขพร้อมกัน** (`needsCustomerQuote()` ใน `src/utils/constants.ts`)

| เงื่อนไข | เพราะ |
|---|---|
| สาขาแฟรนไชส์ (รหัสไม่ขึ้นต้นด้วย `C`) | สาขาบริษัทเครื่องเป็นของบริษัทเอง |
| ใช้อะไหล่ (`needsParts = true`) | ไม่ใช้อะไหล่ก็ไม่มีอะไรให้ขาย |
| หมดประกันแล้ว | ของในประกันผู้ขายรับผิดชอบอยู่แล้ว |

งานที่ไม่เข้าเงื่อนไขข้ามสองขั้นนี้ไปขั้นจ่ายงานเลย

วันหมดประกันคิดจากวันเปิดร้าน + 3 ปี (ดูหัวข้อถัดไป) จึงตอบได้เกือบทุกสาขา
เหลือที่ตอบไม่ได้เฉพาะสาขาที่ไม่รู้แม้แต่วันเปิดร้าน ซึ่ง**ถือว่าหมดประกันแล้วไว้ก่อน** —
ตีว่ายังอยู่ในประกันแล้วส่งช่างไปใส่อะไหล่ฟรี เสียหายกว่าการถามราคาเกินจำเป็น

**แอดมินกด "ไม่ต้องเสนอราคา" เพื่อข้ามได้** ถ้าที่จริงอยู่ในประกันหรือตกลงกันแล้วว่า
บริษัทออกให้ แต่ต้องบอกเหตุผลและประวัติบันทึกไว้ — ข้ามแล้วไปโผล่ที่ขั้นเบิกอะไหล่

##### จ่ายงานให้ทีม ไม่ใช่รายคน

ขั้นที่ 4 จ่ายงานให้ **ทีมช่าง** เพราะทีมเป็นหน่วยที่รับผิดชอบสาขาจริง
ส่วนใครไปจริงในวันนั้นเป็นเรื่องที่รู้ตอนปิดงาน ไม่ใช่ตอนจ่ายงาน — ดู
**ผู้เข้าปฏิบัติงาน** ในหัวข้อตอนปิดงาน

**ทีมมาจากไฟล์ทะเบียนสาขา** ไม่ได้เป็นตารางของตัวเอง เพราะความจริงของการแบ่งทีม
อยู่ที่ไฟล์นั้น ถ้าทำตารางแยกจะมีสองที่ที่บอกว่าทีมไหนมีอยู่บ้าง แล้ววันหนึ่งจะไม่ตรงกัน

**ทีมขึ้นกับประเภทงาน** — ไฟล์มีสองคอลัมน์คือ `ผู้ดูแล CM` (`Branch.zone`) และ
`ผู้ดูแล PM` (`Branch.pmTeam`) งาน PM จึงตั้งต้นด้วยทีม PM ส่วนงาน CM/IT/อื่นๆ
ตั้งต้นด้วยทีม CM เซิร์ฟเวอร์เป็นคนคิดให้ (`suggestedTeam`) ไม่ปล่อยให้หน้าจอตัดสินเอง
ไม่งั้นวันหลังมีหน้าจอที่สามแล้วกฎไม่ตรงกัน

**สาขาที่ไม่ได้ระบุทีม PM ใช้ทีม CM แทน** และหน้าจอบอกไว้ว่าตกมาใช้ทีม CM เพราะอะไร
ในไฟล์จริงมีสาขาแบบนี้ราวหนึ่งในสาม — ทีมที่ไปงาน CM อยู่แล้วเป็นคำตอบที่ใกล้ถูกที่สุด
ที่ไฟล์บอกได้ และเป็นแค่ค่าตั้งต้น เลือกทีมอื่นได้อยู่ดี

**รายการทีมรวมจากทั้งสองคอลัมน์** เพราะบางทีมรับเฉพาะงาน CM (ในไฟล์จริงคือทีมแถบ
กรุงเทพฯ และปริมณฑล) ถ้าอ่านคอลัมน์เดียวทีมเหล่านั้นจะหายไปจากรายการเลือกทั้งที่มีอยู่จริง

**เลือกทีมจาก dropdown** ที่มีช่องค้นหาในตัว เพราะ 22 ทีมเรียงเป็นชิปคือกำแพง
ชิปเต็มจอที่ต้องกวาดตาหาทีละอัน พิมพ์ชื่อทีมสามตัวก็เจอแล้ว และแต่ละทีมบอกไว้ด้วย
ว่าดูแลกี่สาขา

**ทีมของสาขาถูกเลือกไว้ให้เป็นค่าตั้งต้น** และอยู่บนสุดของรายการ
เพราะเป็นคำตอบที่ถูกเกือบทุกครั้ง
**จ่ายข้ามทีมได้** โดยเลือกทีมอื่นจากรายการ — หน้าจอเตือนว่ากำลังข้ามทีมและ
ประวัติบันทึกไว้ว่าข้ามมาจากทีมไหน (`จ่ายงานให้ ทีมเหนือ 1 (ข้ามทีม — สาขานี้เป็นของ ทีมใต้ 1)`)
งานที่ข้ามทีมโดยไม่มีใครรู้คืองานที่ไม่มีใครอธิบายได้ทีหลังว่าทำไมทีมนั้นถึงไปสาขานั้น

ทีมที่ไม่มีในทะเบียนถูกปฏิเสธตั้งแต่ฝั่งเซิร์ฟเวอร์ — ทีมที่สะกดผิดคือใบงานที่ไม่มีใครเห็น
เพราะไม่มีช่างคนไหนสังกัดทีมนั้น

**ใบงานเก่าที่จ่ายรายคนไว้ยังอยู่ในมือคนเดิม** (`WorkOrder.assignedToId` ยังถูกอ่านอยู่
แค่ไม่เขียนค่าใหม่แล้ว) ใบที่ค้างอยู่ตอนเปลี่ยนระบบจึงไม่หายไปจากรายการของคนที่กำลังทำอยู่

##### ประเภทงาน

**ประเภทงาน** เลือกจากสี่แบบ ไม่ใช่พิมพ์เอง

| ค่า | ป้าย | ใช้เมื่อ |
|---|---|---|
| `CM` | งาน CM | ซ่อมแก้เมื่อเครื่องเสีย |
| `PM` | งาน PM | บำรุงรักษาตามรอบ |
| `IT` | งาน IT | งานระบบและเครือข่าย |
| `OTHER` | อื่นๆ | นอกเหนือจากสามแบบข้างบน ต้องระบุรายละเอียด |

เป็นตัวเลือกตายตัวเพราะต้องเอาไปนับแยกในรายงานได้ ข้อความอิสระที่คนพิมพ์เอง
จะได้ "งานCM" "CM" "ซ่อม CM" ปนกันจนรวมยอดไม่ได้

ใบงานเก่าที่เปิดไว้ก่อนเปลี่ยนตัวเลือก (`PROJECT` / `PARTS_CLEARING`) ยังแสดงป้ายเดิมได้
ปกติ — ตัวเลือกที่เลิกใช้ถูกเอาออกจากฟอร์มอย่างเดียว ไม่ได้ลบออกจากตารางป้าย
ไม่งั้นใบงานเก่าจะขึ้นเป็นรหัสดิบให้คนที่เปิดอ่านทีหลังต้องมาเดาเอง

##### ไม่ใช้อะไหล่ก็ข้ามได้

ขั้นที่ 2 หัวหน้าภาคตัดสินก่อนว่า **ใช้อะไหล่** หรือ **ไม่ใช้อะไหล่**

- **ใช้** → ระบุรายการ แล้วส่งให้แอดมินเช็คคลัง (ขั้น 3)
- **ไม่ใช้** → **ข้ามขั้นเช็คคลัง ไปจัดคิวช่างเลย** เช่น ให้เข้าไปประเมินอาการก่อน
  หรืองานที่แค่ปรับตั้ง

การบังคับให้ผ่านขั้นที่ไม่มีอะไรให้ทำ คือการทำให้ใบงานค้างโดยไม่มีเหตุผล
แถบขั้นตอนแสดงขั้นที่ข้ามเป็นขีดฆ่าพร้อมคำว่า "ข้าม — ไม่ใช้อะไหล่"
ไม่ใช่เครื่องหมายถูก เพราะไม่มีใครทำอะไรในขั้นนั้น

##### ปิดงานได้เฉพาะงานที่จบแล้ว

**ผลการทำงานเหลือสองแบบ** — `ซ่อมเสร็จ` กับ `ไปถึงแล้วเครื่องปกติ`

เดิมปิดด้วย "รออะไหล่ ต้องกลับไปอีกรอบ" หรือ "ยังไม่จบ ต้องกลับไปอีกรอบ" ได้
ซึ่งไม่ใช่การปิดงาน มันคือการส่งกลับไปตั้งต้นใหม่ ปล่อยให้ปิดแบบนั้นได้ ใบงานจะขึ้นว่า
`DONE` ทั้งที่เครื่องยังเสีย แล้วตัวเลขงานที่สำเร็จในรายงานจะสวยกว่าความจริง

**จบงานไม่ได้ให้ส่งกลับไปที่หัวหน้าภาค** ด้วยปุ่ม "จบงานไม่ได้ ส่งกลับให้หัวหน้าภาค"
ใบงานย้อนไปขั้นที่ 1 แล้ววนตามสายงานอีกรอบ (ดูหัวข้อถัดไป)

**ต้องบอกเหตุผลเสมอ** ว่าเจออะไรที่หน้างาน และ**แนบรูป/วิดีโอที่เจอได้ด้วย** (ไม่บังคับ) —
หัวหน้าภาคที่รับกลับมาต้องตัดสินใจต่อ คำว่า "บอร์ดไหม้" กับรูปบอร์ดที่ไหม้
พาไปสู่การตัดสินใจคนละแบบ รูปขึ้นก่อนแล้วใบงานค่อยเด้งกลับ ไม่งั้นหัวหน้าภาคที่เปิดดู
พอดีจะเห็นแต่ข้อความแล้วตัดสินใจไปแล้ว

ใบงานเก่าที่เคยปิดด้วยผลสองแบบนั้นยังแสดงป้ายไทยได้ปกติ — เอาออกจากตัวเลือกเฉยๆ
ไม่ได้ลบข้อมูล

##### ไปถึงหน้างานแล้วต้องเปลี่ยนอะไหล่

ช่างที่ถือใบงานกด **"จบงานไม่ได้ ต้องเบิกอะไหล่เพิ่ม — เลือกอะไหล่แล้วส่งกลับ"**
(`POST /:id/reassess-parts`) ใบงานย้อนกลับไปขั้นที่ 1 แล้ววนตามสายงานอีกรอบ

- **ช่างเลือกอะไหล่ที่จะเบิกเพิ่มได้เลย** เพราะเป็นคนเดียวที่เห็นของจริงว่าเสียตรงไหน
  รายการที่เลือกกลายเป็น "อะไหล่ที่ต้องใช้" ของใบงาน และขึ้นรอไว้ในฟอร์มของหัวหน้าภาค
  ไม่ต้องให้ใครมานั่งพิมพ์ซ้ำหรือเดาแทน
- **ยังต้องผ่านหัวหน้าภาคก่อน** ช่างรู้ว่าต้องใช้อะไร หัวหน้าภาครู้ว่าเบิกได้แค่ไหน
  สองอย่างนี้คนละเรื่องกัน หัวหน้าภาคเพิ่ม/ตัดรายการได้ก่อนส่งให้แอดมินเช็คคลัง
- **เลือกอะไหล่หรือไม่เลือกก็ได้** ยังบอกไม่ได้ว่าต้องใช้ตัวไหน (ต้องถอดดูก่อน)
  ก็ส่งกลับเปล่าๆ ให้หัวหน้าภาคเป็นคนระบุแทนได้
- **ต้องบอกด้วยว่าเจออะไรที่หน้างาน** หัวหน้าภาคที่รับกลับมาต้องรู้ถึงจะตัดสินได้ถูก
- วันนัดและผลเช็คคลังรอบก่อนถูกล้าง เพราะไม่ตรงกับที่เจอจริงแล้ว —
  รายการอะไหล่ถูก**แทนที่**ด้วยของที่ช่างขอ ไม่ใช่ต่อท้าย ไม่งั้นแอดมินจะเห็นว่า
  "เช็คแล้ว" ทั้งที่ของที่ต้องใช้เปลี่ยนไปแล้ว
- ประวัติบันทึกทั้งเหตุผลและรายการที่ขอ (`ไปถึงแล้วพบว่าบอร์ดไหม้ — ขอเบิกเพิ่ม: SP-BOARD, SP-BELT x2`)
- **ใบเดิม ไม่ใช่เปิดใบใหม่** ประวัติ เวลาที่ใช้ และเคสที่ผูกอยู่ต้องอยู่ใบเดียวกัน
  ไม่งั้นดูไม่ออกว่างานนี้ไปมาแล้วกี่รอบ
- ย้อนได้เฉพาะตอนที่งานอยู่ในมือช่างแล้ว (`ASSIGNED` / `IN_PROGRESS`)
  ก่อนหน้านั้นยังไม่มีใครไปเห็นหน้างาน

##### ฟอร์มเปิดใบงานถามเฉพาะสิ่งที่ขั้นนี้รู้

สาขา · เครื่อง (รหัส + รุ่น + รูปป้ายรุ่น) · ประเภทงาน · อาการที่พบ · ความเร่งด่วน
· รูป/วิดีโอหน้างาน — จบแค่นั้น

**ไม่มีช่องพิมพ์หัวข้องาน** ระบบตั้งให้จากประเภทงาน (`งาน CM` / `งาน PM` / `งาน IT`)
เพราะช่องพิมพ์อิสระได้ "เครื่องเสีย" "เสีย" "ไปดูหน่อย" ปนกันเป็นร้อยแบบโดยไม่มีใคร
ได้อะไรเพิ่ม — คำอธิบายจริงอยู่ที่**อาการที่พบ**ของแต่ละเครื่อง ซึ่งผูกกับเครื่องถูกตัวกว่า

ประเภท **อื่นๆ** เป็นข้อยกเว้นเดียวที่บังคับให้ระบุรายละเอียด เพราะคำว่า "อื่นๆ"
ไม่ได้บอกอะไรกับคนที่มาอ่านใบงานทีหลัง

**ไม่ถามอะไหล่ ช่าง หรือวันนัด** เพราะเป็นของขั้น 2, 4 และ 5 ตามลำดับ
ถ้าให้กรอกตั้งแต่ตอนเปิด คนเปิดใบงานต้องรู้เรื่องที่ยังไม่มีใครรู้
และค่าที่กรอกไว้จะขัดกับสิ่งที่เจ้าของขั้นกรอกทีหลัง

เลือกสาขาแล้วขึ้นชื่อสาขาให้เห็นด้วย ไม่ใช่แค่รหัส — เห็น `C0006` อย่างเดียว
ไม่มีทางรู้ว่าเลือกถูกใบหรือเปล่าจนกว่าจะเปิดใบงานไปแล้ว

##### วันเปิดร้านและประกัน

เลือกสาขาแล้วขึ้น **วันเปิดร้าน** กับ **สถานะประกัน** ให้เห็นทันที และขึ้นในหน้า
รายละเอียดใบงานด้วย เพราะประกันเป็นตัวตัดสินว่าจะส่งช่างของเราไปหรือให้ผู้ขาย
รับผิดชอบ — ต้องรู้ตั้งแต่ตอนเปิดใบงาน ไม่ใช่ไปรู้ตอนช่างถึงหน้างานแล้ว

**รหัสสาขาขึ้นต้นด้วย `C` คือสาขาบริษัท ไม่มีประกัน** เครื่องเป็นของบริษัทเอง
ระบบตัดรายละเอียดประกันออกตั้งแต่ฝั่งเซิร์ฟเวอร์ ไม่ได้ปล่อยให้หน้าจอไปตัดสินใจเอง
ว่าจะซ่อนไหม ไม่งั้นวันหลังมีหน้าจอที่สามแล้วลืมซ่อน

##### ประกัน 3 ปีนับจากวันเปิดร้าน

**ไม่ต้องกรอกวันหมดประกัน** ระบบคิดให้จากวันเปิดร้าน + 3 ปี ซึ่งเป็นเงื่อนไขมาตรฐาน
ของทุกสาขา

เหตุผลที่คิดเอาแทนที่จะให้กรอก: ทะเบียนจริงมี**วันเปิดร้านครบทั้ง 1,204 สาขา**
แต่**ไม่มีวันหมดประกันสักสาขาเดียว** ถ้ารอให้กรอกทีละสาขา ช่องนี้จะว่างตลอดไป
และขั้นเสนอราคาจะเดาผิดทั้งระบบ — ตอนนี้ตอบได้ทุกสาขาที่รู้วันเปิดร้าน
ซึ่งคือทั้งหมด (จากตัวเลขจริง: สาขาแฟรนไชส์ 245 จาก 774 ยังอยู่ในประกัน
จึงไม่ต้องผ่านขั้นเสนอราคา)

กฎอยู่ที่เซิร์ฟเวอร์ที่เดียว (`warrantyEndFor()` ใน `src/utils/constants.ts`)
ทั้ง API สาขาและใบงานส่งวันที่คิดแล้วออกไป **หน้าจอไม่รู้ว่ากฎกี่ปี** จึงไม่มีทาง
ที่สองหน้าจอจะคิดคนละแบบ และเปลี่ยนเป็น 5 ปีวันหลังก็แก้ที่เดียว

**ค่าที่กรอกเองชนะกฎ** สัญญาบางฉบับต่างออกไป และคนที่ตั้งใจกรอกวันเจาะจง
ย่อมมีเอกสารอยู่ในมือ — แต่ไม่ใช่สิ่งที่ต้องทำเป็นปกติ ใส่ได้ทีละสาขาผ่าน API สาขา
หรือเป็นคอลัมน์ `วันหมดประกัน` ในไฟล์ทะเบียน (รับ `พ.ศ.` ด้วย — 2569 ถูกแปลงเป็น
2026 ให้เอง ไม่งั้นวันหมดประกันจะกลายเป็นยังไม่หมดไปอีกห้าศตวรรษ)
ไฟล์ที่ไม่มีคอลัมน์นี้จะไม่ลบค่าที่เคยกรอกไว้ทิ้ง

ท้ายฟอร์มบอกว่าใบงานจะไปอยู่ที่หัวหน้าภาคคนไหน (ตามภาคของสาขาที่เลือก)
คนเปิดจะได้รู้ว่าส่งไปให้ใคร

##### เปิดทีเดียวหลายเครื่อง แต่ได้ใบงานเครื่องละใบ

ช่างไปสาขาหนึ่งรอบเดียวแต่เจอเสียสามเครื่อง คนละอาการ กด **เพิ่มเครื่องใน
สาขาเดียวกัน** แล้วกรอกรหัสเครื่อง รุ่น อาการ รูปป้ายรุ่น และรูปหน้างาน
แยกทีละเครื่องได้ในฟอร์มเดียว สาขา ประเภทงาน และความเร่งด่วนใช้ร่วมกัน
เพราะเป็นค่าเดียวกันอยู่แล้ว

**แต่ระบบสร้างใบงานเครื่องละใบ ไม่ใช่ใบเดียวที่ถือหลายเครื่อง** เพราะแต่ละเครื่อง
มีอะไหล่ของตัวเอง ปิดคนละเวลา และอาจถูกจ่ายให้ช่างคนละคน ใบเดียวที่ถือสามเครื่อง
จะปิดไม่ได้จนกว่าจะเสร็จครบทั้งสาม ซึ่งไม่ตรงกับที่หน้างานเป็นจริง

- ถ้ามีเครื่องตัวใดตัวหนึ่งผิด **ไม่สร้างใบไหนเลย** — ตรวจให้ครบก่อนแล้วค่อยสร้าง
  ไม่งั้นจะเหลือใบงานค้างครึ่งทางที่คนกดไม่รู้ว่าต้องไปลบทิ้งหรือเปล่า
- ใส่เครื่องซ้ำในคราวเดียวไม่ได้
- **งานทั้งสาขา** (ไม่ระบุเครื่อง) ยังเปิดได้ แต่ได้ใบเดียว ไม่ใช่หลายใบที่ไม่รู้ว่าต่างกันตรงไหน
- เปิดหลายใบเสร็จแล้วระบบพากลับไปหน้ารายการ ไม่ใช่เด้งเข้าใบใดใบหนึ่ง
  ซึ่งจะเหมือนอีกสองใบหายไป

##### หมายเลขเครื่องพิมพ์เอง ไม่ได้เลือกจากทะเบียน

**รหัสเครื่องคือ `W` หรือ `D` ตามด้วยตัวเลข** (`W3` · `D12`) — `W` คือเครื่องซัก
`D` คือเครื่องอบ ตัวอักษรหน้าบอกชนิดเครื่องอยู่ในตัว ระบบจึงไม่ต้องถามซ้ำว่า
เครื่องนี้เป็นซักหรืออบ ฟอร์มแปลงเป็นตัวพิมพ์ใหญ่ให้เอง และเตือนทันทีที่พิมพ์ผิดรูปแบบ
ไม่ใช่ไปเตือนตอนกดบันทึก

**ไม่ได้ดึงรายการเครื่องจากทะเบียนมาให้เลือกแล้ว** ทะเบียนมาจากไฟล์ export
ซึ่งมีเฉพาะเครื่องที่เคยมีปัญหา เครื่องที่ยังไม่เคยเสียจึงไม่อยู่ในนั้น —
คนที่ยืนอยู่หน้าเครื่องจริงและอ่านรหัสจากตัวเครื่องได้ ไม่ควรถูกบล็อกเพราะ
ไฟล์ยังไม่รู้จักเครื่องตัวนั้น **เครื่องที่ยังไม่มีในระบบถูกสร้างให้ตอนเปิดใบงาน**
โดยเดาชนิดจากตัวอักษรหน้ารหัส

**รุ่นของเครื่องเก็บที่ตัวเครื่อง ไม่ใช่ที่ใบงาน** (`Machine.model`) เพราะรุ่นเป็นของ
ตัวเครื่อง ไม่ได้เปลี่ยนไปตามงาน เลือกจาก `Oasis` · `Oasis(TC)` · `Huebsch` ·
`Haier` · `Maytag` หรือ **อื่นๆ** แล้วพิมพ์เอง เป็นตัวเลือกตายตัวด้วยเหตุผล
เดียวกับประเภทงาน — ต้องนับแยกได้ว่ารุ่นไหนเสียบ่อย และเวลาสั่งอะไหล่ต้องรู้ว่ารุ่นอะไร
ปล่อยให้พิมพ์เองล้วนๆ จะได้ `Huebsch` `huebsch` `HUEBSCH` ปนกัน

##### ขนาดเครื่อง (กิโลกรัม)

ข้างๆ หมายเลขเครื่องมีช่อง **ขนาดเครื่อง** (ไม่บังคับ) เลือกจาก `10` `13` `15` `18`
`20` `25` kg หรือ **อื่นๆ** แล้วพิมพ์เลขเอง — รับได้ 5-60 kg กันพิมพ์พลาดอย่าง 500
กดตัวที่เลือกไว้ซ้ำคือเอาออก ไม่ต้องมีปุ่มล้างอีกปุ่ม เพราะช่องนี้ไม่บังคับ
และคนที่กดผิดแล้วยกเลิกไม่ได้จะปล่อยค่าผิดไว้แทนที่จะเว้นว่าง

**เก็บเป็นตัวเลขไม่ใช่ข้อความ** (`Machine.capacityKg Int?`) หน่วยเป็น kg ตายตัว
ทั้งระบบจึงไม่เก็บหน่วยไปด้วย — เก็บ `"10 kg"` เป็นข้อความคือเปิดช่องให้มี `10kg`
`10 กก.` และ `10` อยู่ปนกันจนจัดกลุ่มไม่ได้ว่าขนาดไหนเสียบ่อย
ฝั่งเซิร์ฟเวอร์ประกอบหน่วยให้ตอนส่งออก (`machineCapacityLabel`) หน้าจอจึงไม่ต้องรู้หน่วย

**ต่างจากรุ่นตรงที่พิมพ์เลขนอกรายการได้** รุ่นต้องคุมคำให้ตรงกันเพื่อรวมยอด
แต่ขนาดเป็นตัวเลขอยู่แล้ว เลข 17 ที่พิมพ์เองยังนับรวมกับเลข 17 อื่นได้อยู่ดี
รายการที่ให้กดมีไว้เพื่อความเร็ว ไม่ได้มีไว้บังคับ

**ใช้รายการเดียวกันทั้งเครื่องซักและเครื่องอบ** ไม่ได้แยกตามชนิด เพราะที่หน้างาน
คนอ่านเลขจากป้ายบนตัวเครื่อง ไม่ได้เลือกจากสเปกที่ควรจะเป็นของรุ่นนั้น

##### รุ่นกับขนาดถามครั้งเดียว ครั้งต่อไปขึ้นให้เอง

ทั้งคู่เก็บที่ **ตัวเครื่อง** ไม่ใช่ที่ใบงาน — เครื่อง `W5` ที่เป็น Huebsch ขนาด 13 kg
วันนี้ ก็ยังเป็นตัวเดิมขนาดเดิมในใบงานหน้า ถามซ้ำทุกใบคือการขอให้คนกรอกของเดิม
อีกรอบแล้วเสี่ยงได้คำตอบที่ไม่ตรงกับครั้งก่อน

ฟอร์มถามสาขาก่อน แล้วโหลดเครื่องของสาขานั้นทั้งชุดมารอ
(`GET /api/branches/:code/machines`) พอพิมพ์รหัสตรงกับที่มีอยู่ รุ่นกับขนาดขึ้นให้เอง
— **ถามทีเดียวทั้งสาขา ไม่ได้ถามตอนพิมพ์ทีละตัวอักษร** เพราะพิมพ์ `W12` คือสามจังหวะ
ซึ่งจะกลายเป็นสามคำขอโดยได้คำตอบเดียวกัน

**ไม่ทับค่าที่คนกรอกไปแล้ว** ด้วยเหตุผลเดียวกับผู้ติดต่อ — คนที่ยืนอยู่หน้าเครื่อง
เห็นป้ายจริงอยู่ ย่อมรู้ดีกว่าค่าที่บันทึกไว้เมื่อเดือนก่อน และรุ่นที่เคยพิมพ์เอง
(ไม่อยู่ในรายการ) จะถูกเติมกลับไปที่ช่อง **อื่นๆ** ไม่ใช่หายไปเฉยๆ

ฝั่งเซิร์ฟเวอร์เขียนกลับเฉพาะตอนมีค่าส่งมาและค่าเปลี่ยนจริง — **ไม่ส่งมาแปลว่า
"ไม่รู้" ไม่ใช่ "ไม่มี"** จึงไม่ล้างของเดิมทิ้ง ถ้าถือว่าไม่ส่งมาคือว่าง รุ่นที่เคยกรอกไว้
จะหายไปเพราะใบงานใบอื่นที่ไม่ได้กรอกช่องนี้

##### รูปป้ายรุ่น — ไม่บังคับ แต่ช่วยตอนสั่งอะไหล่

แต่ละเครื่องมีช่องแนบ **รูปป้ายรุ่น** (nameplate) แยกจากรูปอาการ เก็บเป็นไฟล์แนบ
ที่มี `role = "NAMEPLATE"` และขึ้นป้ายกำกับในใบงาน

**ไม่บังคับให้ใส่** เพราะบางเครื่องป้ายลอกไปแล้วหรือถ่ายไม่ถึง — บังคับแล้วคนจะถ่าย
อะไรก็ได้มาให้ผ่าน ซึ่งแย่กว่าไม่มีรูป ที่มีค่าคือรูปที่ตั้งใจถ่ายมาจริง

มีได้เครื่องละรูปเดียว และถูกส่งขึ้นก่อนรูปอาการเสมอ เพราะถ้าเน็ตหลุดกลางทาง
รูปที่ควรรอดคือรูปที่บอกว่าเครื่องนี้รุ่นอะไร ไม่ใช่รูปที่สิบของอาการเดียวกัน

##### ขั้นเช็คอะไหล่

แอดมินตอบทีละตัวว่า **มีของ** (แล้วเลือกจาก dropdown ว่าอยู่คลังไหน จาก 12 คลังใน
`src/documents/warehouses.ts`) หรือ **หมด** ต้องตอบให้ครบทุกตัวจึงจะไปขั้นต่อไปได้

**คลังเป็น dropdown ไม่ใช่ชิป** เพราะ 12 คลังต่ออะไหล่หนึ่งตัวแปลว่าอะไหล่สามตัว
ก็ 36 ชิป กว่าจะเลื่อนถึงช่องเลขใบเบิกข้างล่าง — dropdown ย่อให้เหลือบรรทัดเดียวต่อตัว

**มีตัวไหนหมด ใบงานขึ้นสถานะ "รออะไหล่" ให้เอง** — ช่างไปแล้วก็ซ่อมไม่จบอยู่ดี
สถานะนี้ไหลไปขึ้นบนกระดานติดตามเครื่องเสียตามกลไกปกติ

ระบบไม่ได้รู้ยอดคงเหลือจริง แอดมินเป็นคนตอบจากที่ตัวเองรู้ —
ยังไม่มีข้อมูลสต็อกอะไหล่รายคลังในระบบ

###### เลขใบเบิกอะไหล่

ตอบว่า **มีของ** แล้วต้องใส่ **เลขใบเบิกอะไหล่** จากระบบคลังด้วย ตัวที่ **หมด**
ไม่ต้องใส่ เพราะยังไม่ได้เบิก — ของที่หมดแล้วมีเลขใบเบิกค้างจากรอบก่อนจะถูกล้างให้

บังคับตั้งแต่ฝั่งเซิร์ฟเวอร์ ไม่ใช่แค่ปุ่มสีจาง เพราะของที่หายออกจากคลังโดยไม่มี
เอกสารผูกไว้ จะหาไม่เจอตอนตรวจนับว่าไปอยู่ที่ไหน

**เก็บรายอะไหล่ (`WorkOrderPart.requisitionNo`) ไม่ใช่รายใบงาน** เพราะใบงานที่ช่าง
ส่งกลับมาขอเบิกเพิ่มจะมีใบเบิกใบที่สอง ถ้าเก็บไว้ที่ใบงานใบเดียว เลขใบแรกจะถูกทับหาย

หน้าจอให้กรอกช่องเดียวแล้วใช้กับทุกตัวที่ตอบว่ามีของ เพราะปกติเบิกทีเดียวได้ใบเดียว
การพิมพ์เลขเดิมห้ารอบคือทางที่ทำให้พิมพ์ผิดโดยไม่มีใครรู้ — ถ้าวันหลังต้องเบิกคนละใบจริง
ค่อยเปิดให้แก้รายตัวได้ โดยไม่ต้องแก้ฐานข้อมูลอีก

**ช่องอยู่บนสุดของหน้าเช็ค ไม่ใช่ใต้รายการอะไหล่** อะไหล่ตัวเดียวมีชิปคลังสิบสองอัน
สามตัวก็ยาวเกินหน้าจอไปแล้ว ช่องที่อยู่ใต้รายการจึงเท่ากับไม่มีช่องสำหรับคนที่ไม่ได้
เลื่อนลงไปจนสุด — และเลขใบเบิกเป็นค่าของทั้งใบ ไม่ได้เป็นของอะไหล่ตัวใดตัวหนึ่ง
จึงควรอยู่เหนือรายการอยู่แล้ว

ช่องขึ้นตั้งแต่เปิดหน้า ไม่ได้ซ่อนไว้จนกว่าจะตอบว่ามีของ เพราะช่องที่โผล่มาทีหลัง
เหนือจุดที่คนกำลังมองอยู่ จะดันของที่เหลือเลื่อนลงโดยไม่มีใครทันเห็น
คำเตือนใต้ช่องเปลี่ยนเป็นสีเหลืองเมื่อมีของที่ต้องเบิกแล้วแต่ยังไม่ได้ใส่เลข


อย่าสับสนกับ **สถานะการดำเนินการ** ของเคส (รออะไหล่ / รอช่างเข้าแก้ไข / รอลูกค้าจ่ายเงิน /
รอลูกค้าแจ้งซ่อม) ซึ่งบอกว่า *เคสติดอยู่ที่ขั้นไหน* ส่วนสถานะใบงานบอกว่า *ใบงานเดินไปถึงไหน*

#### ตอนปิดงาน

ช่างกรอกสามอย่าง — **ผลการทำงาน** (ซ่อมเสร็จ / รออะไหล่ ต้องกลับไปอีกรอบ /
ยังไม่จบ ต้องกลับไปอีกรอบ / ไปถึงแล้วเครื่องปกติ) · **สรุปงานที่ทำ** · **อะไหล่ที่ใช้ไป**
(เลือกจากรายการอะไหล่ในระบบ ตัวเดียวกับที่กระดานใช้)

แยก "ซ่อมเสร็จ" ออกจาก "ไปแล้วแต่ยังไม่จบ" เพราะถ้านับรวมกัน ใบงานที่ปิดเพราะรออะไหล่
จะถูกนับเป็นงานที่สำเร็จ แล้วตัวเลขในรายงานสวยกว่าความจริง

##### ผู้ติดต่อที่สาขา

ฟอร์มเปิดใบงานมีช่อง **ชื่อผู้ติดต่อ** กับ **เบอร์ติดต่อสาขา** (ไม่บังคับ) ช่างจะได้รู้ว่า
โทรหาใครก่อนไปหน้างาน และขึ้นในหน้ารายละเอียดใบงาน

**เก็บที่ใบงาน ไม่ได้เก็บที่สาขา** เพราะคนเฝ้าร้านเปลี่ยนตามกะและตามช่วง เบอร์ที่ใช้ได้
เมื่อสามเดือนก่อนไม่ได้แปลว่าวันนี้โทรไปแล้วเจอคนเดิม — ค่าที่บันทึกไว้จึงเป็นของใบงานนั้น

ระบบเติมค่าจากใบงานล่าสุดของสาขาเดียวกันให้ (`GET /api/branches/:code/last-contact`)
ส่วนใหญ่เป็นคนเดิมเบอร์เดิม การให้พิมพ์ใหม่ทุกครั้งคือทางที่ทำให้ช่องนี้ว่าง
และไม่ทับค่าที่คนกรอกไปแล้ว

**ใช้ได้ทั้งเปิดเองและเปิดจากกระดาน** — ทางกระดานเคยมีช่องให้กรอกแต่ไม่ได้ส่งต่อ
คนกรอกพิมพ์ชื่อกับเบอร์ลงไป กดบันทึกแล้วใบงานขึ้นสำเร็จ แต่ค่าที่พิมพ์หายเงียบ
ซึ่งแย่กว่าไม่มีช่องเลย — ไม่มีช่องคนยังรู้ว่าต้องไปถามที่อื่น มีช่องแล้วหายคือเข้าใจว่า
บันทึกไว้แล้ว ตอนนี้ `POST /api/work-orders/from-outage/:id` รับ `contactName`
กับ `contactPhone` เหมือนทางเปิดเอง และรับ `model` กับ `capacityKg` ด้วย
เพราะเคสรู้แค่ว่าเครื่องไหนดับ ไม่รู้ว่ารุ่นอะไรกี่กิโล — คนที่ตอบได้คือคนที่ยืนอยู่
หน้าเครื่องตอนเปิดใบงาน

##### วันเข้างานเป็นของหัวหน้าภาค ไม่ใช่ช่าง

ขั้นที่ 4 หัวหน้าภาคจ่ายงานให้ทีมแล้ว**นัดวันเข้าในขั้นเดียวกัน** เพราะคนที่รู้ว่า
คิวทั้งทีมว่างวันไหนคือคนที่ถือคิวทั้งทีม ช่างคนเดียวตอบได้แค่ว่าตัวเองว่างไหม
ซึ่งไม่พอสำหรับงานที่จ่ายให้ทีม แอดมินทำแทนได้เหมือนทุกขั้น

ช่างเริ่มมีสิทธิ์ตอนขั้นที่ 5 — ไปหน้างาน แล้วปิดงานหรือส่งกลับ

##### สถานะการดำเนินการขึ้นตามขั้นให้เอง

**สถานะการดำเนินการ** (รออะไหล่ / รอช่างเข้าแก้ไข) ไม่ต้องกรอกเองอีกแล้ว
ขั้นของใบงานรู้อยู่แล้วว่าตอนนี้ติดอยู่ที่อะไร:

| ขั้น | สถานะที่ขึ้นให้ |
|---|---|
| เช็คอะไหล่แล้วมีตัวหมด | รออะไหล่ |
| เช็คอะไหล่แล้วครบ · จ่ายงาน · นัดวัน | รอช่างเข้าแก้ไข |
| ปิดงาน | ล้างทิ้ง |

ให้คนมากรอกซ้ำคือการขอให้คนพิมพ์สิ่งที่ระบบรู้อยู่แล้ว แล้วก็จะไม่ได้พิมพ์ —
ผลคือกระดานติดตามเครื่องเสียขึ้นสถานะค้างจากเมื่อสองสัปดาห์ก่อน

**รอลูกค้าจ่ายเงิน** กับ **รอลูกค้าแจ้งซ่อม** ยังต้องกรอกเองอยู่ เพราะเป็นเรื่อง
ฝั่งลูกค้าที่ขั้นของใบงานไม่มีทางรู้

##### ต้องบอกว่าใครเข้าไปทำ

หน้าปิดงานถาม **ผู้เข้าปฏิบัติงาน** เป็นช่องเลือก 3 ช่อง — **คนที่ 1 / 2 / 3**
บวกช่องพิมพ์สำหรับคนที่ไปด้วยแต่ไม่มีบัญชีในระบบ เช่น ผู้รับเหมาหรือคนของสาขา
ต้องมีอย่างน้อยหนึ่งชื่อไม่ทางใดก็ทางหนึ่ง

**สามช่อง ไม่ใช่เลือกจากรายชื่อทั้งหมด** เพราะทีมหนึ่งไปกันไม่เกินสามคน การให้กด
เลือกจากรายชื่อช่างทั้งบริษัทแปลว่าต้องกวาดตาหาชื่อในกองที่ไม่เกี่ยวข้อง และกดเกิน
ไปหนึ่งคนก็ไม่มีอะไรบอกว่าเกิน — สามช่องบอกจำนวนสูงสุดด้วยตัวมันเอง
(เซิร์ฟเวอร์กันไว้ที่สามเหมือนกัน) คนเดียวกันเลือกซ้ำสองช่องไม่ได้ เพราะคนที่เลือก
ไปแล้วถูกตัดออกจากตัวเลือกของช่องที่เหลือ

จำเป็นเพราะ**งานถูกจ่ายให้ทีม ไม่ได้จ่ายรายคน** ชื่อคนที่ไปจริงจึงมีอยู่ที่เดียวคือตรงนี้
ปล่อยว่างได้เมื่อไหร่ ก็จะว่างเกือบทุกใบ แล้วคำถามว่า "ใครไปสาขานี้" จะตอบไม่ได้เลย
ทั้งที่เป็นคำถามพื้นฐานที่สุดของการจ่ายงานเป็นทีม

ต่างจาก **ปิดโดย** ซึ่งเป็นคนที่กดปุ่ม — ทีมหนึ่งไปหลายคนแต่คนที่กดปิดมีคนเดียว

เก็บเป็นตาราง (`WorkOrderWorker`) ไม่ใช่ข้อความรวมกัน เพราะต้องนับย้อนได้ว่าใครไปกี่งาน

##### ต้องแนบรูปหรือวิดีโอหน้างาน

ปิดงานไม่ได้จนกว่าจะมี **รูป / วิดีโอหน้างาน** อย่างน้อยหนึ่งไฟล์ (นับเฉพาะไฟล์ที่ไม่มี
`role` — ใบเหลืองกับป้ายรุ่นเป็นเอกสารและข้อมูลของเครื่อง ไม่ใช่ภาพของงานที่ทำ)

รูปหน้างานคือสิ่งเดียวที่บอกได้ว่าไปถึงจริงและเจออะไร สรุปงานที่พิมพ์มาเป็นคำบอกเล่า
ส่วนรูปเป็นหลักฐาน ใบงานที่ปิดโดยไม่มีรูปเลยคือใบที่ตรวจย้อนไม่ได้

##### ป้ายรุ่นต้องถ่ายใหม่ทุกรอบที่ปิดงาน

ปิดงานไม่ได้จนกว่าจะแนบ **รูปป้ายรุ่นที่ถ่ายรอบนี้** และหน้าจอขึ้นให้ด้วยว่าในระบบ
บันทึกเครื่องและรุ่นอะไรไว้ (`W41 · Oasis`) จะได้เทียบกันตรงนั้นเลย

เป็นการ**ไล่เทียบว่าไปถูกเครื่อง** — รุ่นที่กรอกไว้ตอนเปิดใบงานมาจากคนที่อาจไม่ได้
ยืนอยู่หน้าเครื่อง ส่วนรูปนี้ถ่ายตอนทำงานเสร็จ เทียบกันแล้วรู้ทันทีว่าช่างไปถูกเครื่อง
หรือเปล่า และรุ่นที่สั่งอะไหล่ไปตรงกับตัวจริงไหม

**รูปที่ถ่ายไว้ตั้งแต่ตอนเปิดใบงานใช้แทนไม่ได้** เพราะมันตอบได้แค่ว่าเครื่องรุ่นอะไร
ไม่ได้ตอบว่าคนที่ไปวันนั้นอยู่หน้าเครื่องตัวไหน — นับเฉพาะรูปที่แนบหลังจากถูกจ่าย
ให้ทีมรอบล่าสุด เหมือนกฎของใบเหลือง

**ตอนเปิดใบงานยังไม่บังคับเหมือนเดิม** เพราะคนเปิดใบงานบางทีรับแจ้งมาทางโทรศัพท์

##### ใส่อะไหล่ที่ใช้แล้วต้องแนบรูปใบเหลือง

กรอก **อะไหล่ที่ใช้ไป** แล้วหน้าปิดงานจะขอ **รูปใบเบิกอะไหล่ (ใบเหลือง)** ด้วย
เก็บเป็นไฟล์แนบที่มี `role = "REQUISITION"` และขึ้นป้ายกำกับ "ใบเหลือง" บนรูป

**ปิดงานไม่ได้จนกว่าจะแนบ** และเซิร์ฟเวอร์เช็คซ้ำอีกชั้น ไม่ใช่แค่ปุ่มสีจาง —
ใบเหลืองคือหลักฐานว่าของที่หายไปจากคลังไปอยู่ที่เครื่องตัวไหน ถ้าปล่อยให้ปิดได้
โดยไม่มี ก็จะไม่มีใครถ่ายมาเลย แล้วตอนตรวจนับคลังจะเหลือแต่ตัวเลขที่ไม่มีเอกสารรองรับ

ต่างจาก**รูปป้ายรุ่น**ที่ไม่บังคับ เพราะป้ายรุ่นเป็นข้อมูลอ้างอิงที่ขาดไปก็ยังทำงานต่อได้
ส่วนใบเหลืองเป็นเอกสารทางบัญชีที่ต้องมีคู่กับของที่ออกจากคลังเสมอ

**งานที่ไม่ได้ใช้อะไหล่ปิดได้ตามปกติ** ไม่มีการเบิกก็ไม่มีใบเบิกให้ถ่าย

**ต้องเป็นใบเหลืองของรอบนี้** ไม่ใช่ว่าเคยแนบไว้แล้วก็ผ่าน — ใบงานที่ช่างส่งกลับไป
ประเมินอะไหล่ใหม่แล้ววนกลับมา เป็นการเบิกของอีกชุดและมีใบเบิกใบใหม่ ระบบนับเฉพาะ
ใบที่แนบ**หลังจากถูกจ่ายให้ทีมรอบล่าสุด** ถ้านับรวมใบเก่า รอบที่สองจะผ่านไปโดยไม่มี
เอกสารของตัวเอง

##### การ์ดผลการทำงานเก็บของรอบที่ปิดจริง

การ์ด **ผลการทำงาน** แสดง **รูปที่ส่งตอนปิดงาน** ไว้ด้วย — รูปหน้างาน ป้ายรุ่น
และใบเหลืองของรอบที่ปิด พร้อมป้ายกำกับว่าอันไหนเป็นอะไร กดดูไฟล์เต็มได้

เป็น**เฉพาะไฟล์ของรอบที่ปิดจริง** ไม่ใช่ทุกรูปตั้งแต่เปิดใบงาน เพราะใบที่เข้าหน้างาน
หลายรอบมีรูปปนกันหลายรอบ คนที่เปิดมาดูใบที่ปิดแล้วอยากเห็นว่า "รอบที่จบ เขาถ่าย
อะไรมา" ไม่ใช่กองรูปทั้งหมดตั้งแต่ต้น (กองทั้งหมดยังดูได้ที่การ์ดรูป/วิดีโอหน้างาน)

หน้าจอใช้รายการไฟล์ที่การ์ดรูป/วิดีโอโหลดมาแล้ว ไม่ได้ยิงขอซ้ำ เพราะรูปย่อเป็น
data URL ก้อนใหญ่ ขอสองรอบคือโหลดของเดิมสองเท่าโดยไม่ได้อะไรเพิ่ม

##### สถานะที่แสดงมาจากขั้นของใบงาน

ช่อง **สถานะ** ในการ์ดอาการ/สถานะ ขึ้นค่าที่กรอกไว้ก่อน ถ้าไม่มีก็ขึ้น**ชื่อขั้นของ
ใบงาน**แทน (`รอหัวหน้าภาคจ่ายงาน` · `ปิดงานแล้ว`) ไม่ใช่คำว่า "ยังไม่ระบุ"

เพราะขั้นของใบงานบอกได้อยู่แล้วว่าตอนนี้รออะไร คำว่า "ยังไม่ระบุ" จึงเป็นการบอกว่า
ไม่รู้ทั้งที่รู้ — และดูแปลกที่สุดบนใบที่ปิดไปแล้ว ซึ่งเคยขึ้นว่ายังไม่ระบุทั้งที่จบเรียบร้อย

##### ปิดงานแล้วอาการหายจริงไหม

ใบงานที่ปิดแล้วและ**เปิดมาจากเคสบนกระดาน** จะขึ้นผลเทียบกับไฟล์รายงานเครื่องรอบล่าสุด
ในการ์ดผลการทำงาน:

| ผล | หมายความว่า |
|---|---|
| **อาการหายแล้ว** (เขียว) | เครื่องหายไปจากไฟล์รายงานแล้ว พร้อมวันที่ |
| **อาการยังไม่หาย** (แดง) | ปิดใบงานแล้วแต่เครื่องยังขึ้นว่าดับอยู่ |

เพราะ **ปิดใบงาน ≠ เครื่องกลับมา** ช่างเปลี่ยนอะไหล่แล้วเครื่องยังไม่กลับมาก็มี
และต้องเห็นว่าเป็นแบบนั้น ไม่ใช่กลบด้วยการถือว่าปิดงานแล้วจบ

ใบที่**เปิดเอง** ไม่ได้ผูกกับเคสไหน จึงเทียบไม่ได้ และหน้าจอบอกตรงๆ ว่าเทียบไม่ได้
แทนที่จะขึ้นเขียวให้เข้าใจผิดว่าหายแล้ว

ทุกครั้งที่ใบงานขยับ (เปิด มอบหมาย รับงาน ปิด ยกเลิก) ถูกบันทึกไว้ในประวัติของใบงานนั้น
พร้อมว่าใครทำและเมื่อไหร่ — เหมือนประวัติการกรอกอาการของเคส

รหัสใบงานตั้งจาก id (`WO-00042`) ไม่ได้นับแถวก่อนแล้วบวกหนึ่ง เพราะการนับจะชนกันทันที
ถ้ามีคนกดพร้อมกันสองคน ซึ่งเป็นเรื่องปกติตอนเช้าที่ทุกคนเปิดงานพร้อมกัน

#### ลบใบงาน ต่างจากยกเลิกยังไง

ที่ท้ายใบงานมีปุ่ม **ลบใบงานนี้ถาวร** ขึ้นให้**แอดมินเท่านั้น** ช่างและหัวหน้าภาคไม่เห็นปุ่มนี้
และถึงยิง `DELETE` ตรงก็ถูกปฏิเสธ ไม่ได้ซ่อนแค่ปุ่มแล้วปล่อยหลังบ้านเปิด

| | ยกเลิกใบงาน | ลบใบงาน |
|---|---|---|
| ใครทำได้ | แอดมิน · หัวหน้าภาคในภาคตัวเอง | แอดมินเท่านั้น |
| ใบงานหลังทำ | ยังอยู่ ขึ้นว่ายกเลิกแล้ว | หายไปทั้งใบ |
| ร่องรอย | เหลือว่าใครยกเลิกเมื่อไหร่ เพราะอะไร | ไม่เหลืออะไรในระบบ |
| ใช้เมื่อ | เปิดใบถูก แต่ไม่ได้ทำแล้ว | เปิดผิด เปิดซ้ำ หรือใบทดสอบ |

**ของจริงที่ควรใช้เกือบทุกครั้งคือยกเลิก** เพราะใบที่เปิดถูกแล้วไม่ได้ทำก็เป็นข้อมูลอยู่ —
ปีหนึ่งมีใบที่เปิดแล้วไม่ได้ทำกี่ใบ เพราะอะไร เป็นเรื่องที่ตอบได้ต่อเมื่อใบยังอยู่
ลบมีไว้สำหรับใบที่**ไม่ควรมีตั้งแต่แรก** เปิดผิดสาขา กดซ้ำสองใบ หรือใบที่เปิดไว้ลองระบบ
กล่องยืนยันจึงเขียนไว้ตรงๆ ว่าถ้าใบนี้เปิดถูกแต่ไม่ได้ทำ ให้ใช้ยกเลิกแทน

ลบแล้วหายไปด้วยทั้งหมด: อะไหล่ที่ขอเบิกและที่ใช้จริง ประวัติทุกบรรทัด ผู้เข้าปฏิบัติงาน
และ**ไฟล์ในที่เก็บไฟล์ด้วย** ไม่ใช่ลบแค่แถวในฐานข้อมูลแล้วทิ้งรูปค้างไว้กินพื้นที่ตลอดไป
กล่องยืนยันนับให้ก่อนว่าจะเสียอะไรไปกี่รายการ — `อะไหล่ 2 รายการ · ไฟล์แนบ 5 ไฟล์ · ประวัติ 8 รายการ`
เพราะ "ลบใบงาน" ฟังดูเหมือนเสียใบเดียว ทั้งที่จริงเสียรูปหน้างานกับใบเหลืองไปด้วย

ลบไฟล์ทำ**หลัง**ลบในฐานข้อมูลสำเร็จแล้ว และถ้าลบไฟล์ไม่ผ่านก็ไม่ย้อนการลบใบงาน
แต่ตอบกลับมาว่าเหลือไฟล์ที่ลบไม่ได้กี่ไฟล์ (`fileErrors`) เพราะถ้าทำกลับกัน —
ลบไฟล์ก่อนแล้วฐานข้อมูลพัง — จะได้ใบงานที่ยังอยู่แต่รูปหายหมด ซึ่งแย่กว่าไฟล์ค้างในที่เก็บ

ทุกการลบเขียน log ฝั่งเซิร์ฟเวอร์ไว้ว่าใครลบใบไหน พร้อมจำนวนลูกที่หายไปด้วย
ในระบบไม่เหลือร่องรอยแล้ว แต่ใน log ของเซิร์ฟเวอร์ยังตามได้

เคสบนกระดานติดตามเครื่องเสีย **ไม่ได้ถูกลบไปด้วย** เพราะเคสมาจากไฟล์รายงานของบริษัท
ไม่ได้มาจากใบงาน ลบใบงานที่เปิดผิดแล้วเคสยังขึ้นว่าเครื่องดับอยู่ ซึ่งถูกแล้ว —
เครื่องยังดับจริง สิ่งที่ผิดคือใบงาน ไม่ใช่เคส

#### รูปและวิดีโอหน้างาน

ในใบงานมีการ์ด **รูป / วิดีโอหน้างาน** ช่างกดถ่ายรูป เลือกรูป หรือแนบคลิปสั้นได้
ทุกคนที่เปิดใบงานนั้นได้ก็เห็น — ช่างเห็นเฉพาะใบที่ถูกจ่ายให้ตัวเอง หัวหน้าภาคเห็นเฉพาะภาคตัวเอง
แอดมินเห็นทุกใบ กติกาเดียวกับหน้ารายการใบงาน ไม่ใช่กติกาแยกอีกชุด

ทุกวันนี้ช่างถ่ายรูปส่งไลน์ ซึ่งหายไปกับแชทภายในสองสัปดาห์ พอมีเรื่องต้องย้อนดูว่า
ตอนนั้นเครื่องเป็นยังไงก็ไม่เหลืออะไร ที่นี่รูปอยู่ติดกับใบงาน ไม่ต้องไปตามหาในแชทใคร

##### ไฟล์ไม่ได้อยู่ในฐานข้อมูล

รูปอะไหล่เก็บใน Postgres ได้เพราะมีตัวละรูป ทั้งระบบไม่กี่ร้อยรูป แต่ไฟล์แนบใบงานคนละเรื่อง —
งานละ 3-5 รูป บางงานมีวิดีโอ คลิปเดียวหนึ่งนาทีใหญ่กว่าข้อมูลทั้งระบบรวมกัน
และพื้นที่ฐานข้อมูลแพงกว่าพื้นที่เก็บไฟล์ประมาณร้อยเท่าโดยไม่ได้อะไรกลับมา

ไฟล์จริงจึงไปอยู่บน **Supabase Storage** ฐานข้อมูลเก็บแค่ที่อยู่ของไฟล์กับรูปย่อ

เลือกเจ้านี้เพราะแผน Supabase Pro ที่โปรเจกต์จ่ายอยู่แล้วรวมที่เก็บไฟล์ 100 GB
กับ bandwidth 250 GB/เดือนมาให้ในตัว การไปเปิดบัญชีที่เก็บไฟล์อีกเจ้าจึงเพิ่มบิล
เพิ่มคีย์ เพิ่มหน้า dashboard ที่ต้องดูแล โดยไม่ได้พื้นที่เพิ่มในทางปฏิบัติ

`src/storage/fileStore.ts` เป็น S3 มาตรฐานทั้งไฟล์ ไม่มีอะไรผูกกับ Supabase —
ถ้าวันหนึ่งไฟล์โตจน bandwidth ใกล้เพดาน ย้ายไป Cloudflare R2 (ไม่คิดค่าโหลดออก)
ทำได้ด้วยการเปลี่ยนค่า `STORAGE_*` ใน .env ไม่ต้องแก้โค้ด

**รูปย่อเก็บในฐานข้อมูลโดยตั้งใจ** (ไม่กี่สิบ KB) เพราะถ้าเก็บแต่ที่อยู่ หน้าใบงานจะเห็น
แต่ชื่อไฟล์ หัวหน้าภาคที่ไล่ดูยี่สิบใบต้องกดเปิดทีละใบยี่สิบครั้ง และถ้าวันหนึ่ง
ไฟล์ในถังถูกย้ายหรือลบ อย่างน้อยยังเหลือภาพให้รู้ว่าเคยมีอะไร

##### ถังไม่เปิดสาธารณะ

รูปพวกนี้เป็นภาพหน้าร้านลูกค้า ป้ายชื่อสาขา บางทีติดคนในภาพ ถ้าเปิดถังเป็น public
ใครเดา URL ถูกก็เปิดดูได้โดยไม่ต้องล็อกอิน เวลาจะดูไฟล์เต็มระบบจึงขอ**ลิงก์ชั่วคราว
อายุ 2 ชั่วโมง**ให้ทีละครั้ง เท่ากับลิงก์โหลดเอกสารที่ระบบใช้อยู่แล้ว

ไฟล์ไม่ได้วิ่งผ่าน backend ตอนเปิดดู — ที่เก็บส่งตรงถึงเครื่องคนดู เพราะวิดีโอ 50 MB
ที่วิ่งผ่านเซิร์ฟเวอร์จะกินแรมและกินเวลาของ request อื่นไปด้วย

##### ย่อรูปก่อนส่งเสมอ

แอปย่อรูปให้กว้าง 1600 px ก่อนอัปทุกครั้ง ไม่ได้แค่ลดคุณภาพ — การลด `quality`
อย่างเดียวยังได้ไฟล์ 1.5-2.5 MB เพราะความกว้างเท่าเดิม ต้องลดขนาดภาพจริงถึงจะเหลือ
หลักแสนไบต์ ที่ 1600 px ยังเห็นรอยรั่วหรือรหัส error ได้ชัดเท่ากัน

คนที่ได้ประโยชน์ที่สุดคือช่างหน้างานที่เน็ตไม่ดี — การรอส่งรูป 3 MB ผ่าน 4G ในซอย
คือเหตุผลที่คนเลิกส่งรูป

| อย่าง | เพดาน |
|---|---|
| รูป | 10 MB (เผื่อกรณีย่อไม่ทำงาน ปกติเหลือไม่ถึง 1 MB) |
| วิดีโอ | 60 MB ≈ 1080p ประมาณหนึ่งนาที |
| ต่อใบงาน | 20 ไฟล์ |

วิดีโอที่ยาวกว่าหนึ่งนาทีไม่ได้ช่วยให้ใครเข้าใจอาการมากขึ้น แต่ค่าที่เก็บโตตามความยาวตรง ๆ

##### ลบได้เฉพาะคนที่แนบเองกับแอดมิน

รูปหน้างานเป็นหลักฐาน คนที่มีเหตุผลจะลบมีแค่สองแบบ คือคนที่เพิ่งอัปผิดรูป
กับแอดมินที่ต้องเอาของที่ไม่ควรอยู่ในระบบออก การแนบและการลบถูกบันทึกในประวัติของใบงาน

##### ตั้งค่า

ใส่ค่าใน `backend/.env` (ตอน deploy ใส่ใน Environment ของ Render แทน):

1. ที่ Supabase เมนู **Storage** สร้างถังชื่อ `service-app` — **อย่าติ๊ก Public bucket**
2. ไปที่ **Project Settings → Storage → S3 Connection** จดค่า Endpoint กับ Region
   แล้วกด **New access key** เพื่อเอาคีย์สองตัว

```bash
STORAGE_ENDPOINT="https://<project-ref>.supabase.co/storage/v1/s3"
STORAGE_REGION="ap-southeast-1"   # ต้องตรงกับที่หน้านั้นบอก
STORAGE_ACCESS_KEY_ID="..."
STORAGE_SECRET_ACCESS_KEY="..."
STORAGE_BUCKET="service-app"
```

ถ้าไม่ใส่ ระบบอื่นทั้งหมดยังทำงานปกติ แค่กดแนบรูปแล้วจะขึ้นว่ายังไม่ได้ตั้งค่าที่เก็บไฟล์

**เช็คว่าต่อได้จริงไหมโดยเปิด `GET /health/storage` ด้วยบัญชีแอดมิน** — จะบอกว่าพังขั้นไหน
(ยังไม่ใส่ค่า / คีย์ผิดหรือ region ไม่ตรง / ชื่อถังผิด / คีย์เขียนไม่ได้ / ลิงก์ชั่วคราว
เปิดไม่ได้) เพราะทุกกรณีอาการที่ผู้ใช้เห็นเหมือนกันหมดคือ "อัปรูปไม่ขึ้น" แต่แก้คนละทาง

การเช็คนี้ลองถึงขั้นขอลิงก์ชั่วคราวแล้วเปิดไฟล์จริง ไม่ใช่แค่เขียนไฟล์ได้ เพราะ
`STORAGE_REGION` ที่ผิดจะอัปขึ้นได้ปกติแต่ไม่มีใครเปิดรูปดูได้สักคน — ความพังแบบที่
จะไปโผล่ตอนช่างกดรูปหน้างาน ไม่ใช่ตอนตั้งค่า

### เวลากดบันทึกแล้วช้า — หาสาเหตุยังไง

อาการเดียวกันมีได้สามสาเหตุ และแก้คนละทางสุดขั้ว เช็คตามลำดับนี้

**1. เซิร์ฟเวอร์เพิ่งตื่น** — Render free tier หลับเมื่อไม่มีคนใช้ 15 นาที
ครั้งแรกของวันจึงรอ 40-60 วินาที ครั้งต่อ ๆ ไปเร็วปกติ
สังเกตง่าย: **ช้าเฉพาะครั้งแรก** ถ้าเป็นแบบนี้ ให้มีตัวยิง `/health` ทุก 5 นาที

**2. ฐานข้อมูลอยู่ไกลจากเซิร์ฟเวอร์** — เปิด `GET /health/db` ด้วยบัญชีแอดมิน
จะบอกเวลาไปกลับฐานข้อมูลหนึ่งรอบ

| ค่าที่ได้ | แปลว่า |
|---|---|
| < 30 ms | ปกติ |
| 30-80 ms | เริ่มรู้สึก |
| > 80 ms | อยู่คนละ region กัน — ย้ายให้อยู่ region เดียวกับ Supabase |

การเปิดใบงานหนึ่งใบคุยกับฐานข้อมูล **ประมาณ 13 รอบ** คูณดูได้เลย — ที่ 200 ms
ต่อรอบคือรอเกือบสามวินาทีโดยที่โค้ดไม่ได้ผิดอะไรเลย

**3. ต่อฐานข้อมูลผิดโหมด** — ถ้า `DATABASE_URL` ชี้ไปที่ **transaction pooler
(พอร์ต 6543)** ทุกคำสั่งจะจ่ายค่าเปิดการเชื่อมต่อใหม่ เพราะ pooler โหมดนั้นจับคู่
การเชื่อมต่อจริงใหม่ทุก transaction และคำสั่งเดี่ยวของ Prisma นับเป็นหนึ่ง transaction

โหมดนั้นมีไว้สำหรับ serverless ที่โปรเซสเกิดดับตลอดเวลา ส่วน backend นี้เป็น Node
process ตัวเดียวที่เปิดค้างไว้ จึงควรใช้ **session pooler (5432)** ที่จับคู่ครั้งเดียวแล้วใช้ยาว

วัดจากของจริงบน production:

| | 6543 (transaction) | 5432 (session) |
|---|---|---|
| ต่อหนึ่งรอบไปกลับ | 1,157 ms | **234 ms** |
| บันทึกใบงานหนึ่งใบ | ~15 วินาที | **~3 วินาที** |

**เร็วขึ้นห้าเท่าจากการเปลี่ยนพอร์ตอย่างเดียว ไม่ได้แก้โค้ดเลย** และอย่าใส่
`?pgbouncer=true` กับ session pooler เพราะมันปิด prepared statements โดยไม่จำเป็น

ดูจาก `/health/db` ได้ว่าตอนนี้ใช้โหมดไหน — ช่อง `database.mode` กับ `diagnosis`
ซึ่งเทียบเวลาของห้าคำสั่งในการเชื่อมต่อเดียวกับห้าคำสั่งแยกกัน แล้วบอกว่าที่ช้าคือ
การเปิดการเชื่อมต่อหรือระยะทาง

**4. รูปใหญ่** — แอปย่อรูปในเครื่องก่อนส่ง ซึ่งรูปจากมือถือ 12 ล้านพิกเซล
ใช้เวลาราว **2 วินาทีต่อรูปบนคอมพิวเตอร์ และนานกว่านั้นบนมือถือ**
แต่ตรงนี้เกิดตอน**เลือกรูป** ไม่ใช่ตอนกดบันทึก และมีตัวหมุนบอกอยู่ว่า "กำลังย่อรูป"
ตอนกดบันทึกเหลือแค่ส่งไฟล์ที่ย่อแล้ว (ไม่ถึง 1 MB ต่อรูป)

### รายงาน

เมนู **รายงาน** ในแท็บหน้าหลัก มีสี่ใบ แยกตามคนอ่านและจังหวะที่ใช้ ไม่ใช่แยกตามหมวดข้อมูล
เพราะรายงานใบเดียวที่พยายามตอบทุกคนมักไม่มีใครอ่าน

| ใบ | คนอ่าน | ตอบคำถาม |
|---|---|---|
| **ใบงานวันนี้** | หัวหน้าช่าง · ช่างแต่ละโซน | วันนี้ต้องไปที่ไหนก่อน |
| **สรุปรายสัปดาห์** | ผจก.ภาค · หัวหน้าทีม | ภาคของฉันดีขึ้นหรือแย่ลง |
| **ภาพรวมผู้บริหาร** | ผู้บริหาร | เดือนนี้ดีขึ้นกว่าเดือนที่แล้วไหม |
| **อะไหล่ที่ต้องสั่ง** | ฝ่ายจัดซื้อ · คลัง | ต้องสั่งอะไรเข้ามาบ้าง |

ทุกใบดูบนหน้าจอได้ และมีปุ่ม **ดาวน์โหลด Excel** ใช้กลไกเดียวกับเอกสารขอโอนสินค้า
(ไฟล์อยู่ในหน่วยความจำ ลิงก์มีกุญแจของตัวเองและหมดอายุใน 2 ชั่วโมง)

- **หน้าจอกับไฟล์ Excel ใช้ตัวเลขชุดเดียวกัน** คำนวณที่ `src/machines/reports.ts` ที่เดียว
  ถ้าแยกกันคำนวณจะเพี้ยนกันเมื่อไหร่ก็ได้โดยไม่มีใครรู้
- **หน้าจอตัดที่ 25 รายการต่อหมวด** มีปุ่มกดดูเพิ่ม ส่วนไฟล์ Excel มีครบทุกแถวเสมอ
  ใบงานที่มีสองร้อยรายการไม่ใช่ใบงานแล้ว แต่ไฟล์ที่เอาไปทำต่อต้องครบ
- **ใบงานวันนี้ไม่รวมเคสที่รอลูกค้า** (รอจ่ายเงิน / รอแจ้งซ่อม) เพราะช่างลงมือไม่ได้
- **ใบรายเดือนบอกตรง ๆ เมื่อยังไม่มีข้อมูลพอ** ถ้ายังไม่มีเคสที่ปิดแล้วจะขึ้นคำเตือน
  ไม่ปล่อยให้เห็นเลขศูนย์แล้วเข้าใจว่าไม่มีปัญหา

เรียกผ่าน API ได้ที่ `GET /api/machines/reports/:kind` — ใส่ `?format=xlsx` เพื่อขอลิงก์ดาวน์โหลด

### เอกสารขอโอนสินค้า (Word / PDF)

เมนู **เอกสารขอโอนสินค้า** ในแท็บหน้าหลัก กรอกคลังต้นทาง คลังปลายทาง และรายการของ
แล้วเลือกได้ว่าจะออกเป็นไฟล์ไหน — ทั้งสองแบบหน้าตาเหมือนกันตามแบบฟอร์มบริษัท

| ปุ่ม | ได้อะไร | เหมาะกับ |
|---|---|---|
| **ออกเป็น Word** | ไฟล์ `.docx` ดาวน์โหลดลงเครื่อง | ต้องแก้ต่อ เช่น เติมเลขที่เอกสาร เพิ่มบรรทัด |
| **ออกเป็น PDF** | ไฟล์ `.pdf` เปิดดูในเบราว์เซอร์ทันที กดเซฟหรือส่งต่อได้ | ส่งให้คนอนุมัติ หรือสั่งพิมพ์เลย |

**ฟีเจอร์นี้ไม่ต้องใช้ API key และไม่มีค่าใช้จ่าย** ทำงานได้เลยหลังจาก deploy

- **คลังต้นทาง/ปลายทาง** เลือกจาก dropdown รายชื่อคลังของบริษัท
  ถ้าเป็นคลังที่ยังไม่มีในรายการ เลือก "อื่น ๆ (พิมพ์เอง)" แล้วพิมพ์ได้
  เลือกคลังเดียวกันทั้งสองช่องจะถูกเตือนก่อนออกเอกสาร
- ช่อง **รหัสสินค้า** ค้นจากฐานข้อมูลอะไหล่ได้ พิมพ์รหัสหรือชื่อในช่องค้นหาแล้วกดผลลัพธ์
  ระบบจะเติมรหัสและชื่อทางการให้ ส่วนอะไหล่ที่ยังไม่มีในระบบก็พิมพ์เองในบรรทัดได้
- **ผู้จัดทำ** เติมจากชื่อผู้ที่ล็อกอินอยู่ ไม่ต้องกรอก
- **วันที่เอกสาร** เป็นวันที่วันนี้แบบ พ.ศ. (เช่น 6 สิงหาคม 2569)
- **เลขที่เอกสาร** เว้นว่างได้ ไว้กรอกในเอกสารทีหลัง เพราะระบบไม่รู้เลขที่รันของบริษัท
- ถ้ามีรหัสที่ไม่พบในฐานข้อมูล ระบบยังออกเอกสารให้ แต่ขึ้นเตือนไว้ให้ตรวจก่อนส่งอนุมัติ
- คลังต้นทาง/ปลายทางที่ใช้ล่าสุดถูกจำไว้ในเครื่อง เปิดครั้งหน้าไม่ต้องพิมพ์ใหม่
- ลิงก์ดาวน์โหลดมีอายุ **2 ชั่วโมง** ส่งต่อให้คนอนุมัติได้ในช่วงนั้น หมดอายุแล้วออกใหม่

**เพิ่ม/แก้/ลบรายชื่อคลัง** แก้ที่ `backend/src/documents/warehouses.ts` ไฟล์เดียว
แล้ว deploy backend ใหม่ — แอปดึงรายชื่อผ่าน `GET /api/documents/warehouses` ตอนเปิดหน้า
จึงไม่ต้อง build แอปใหม่และไม่ต้องรอให้ทุกคนอัปเดตแอป

ไฟล์แม่แบบต้นฉบับที่ใช้อ้างอิงรูปแบบเก็บไว้ที่ `docs/transfer-request-template.docx`

**โครงสร้างโค้ดที่ประกอบเอกสาร** (`backend/src/documents/`)

| ไฟล์ | หน้าที่ |
|---|---|
| `transferContent.ts` | ข้อความ ลำดับหัวข้อ ชื่อคอลัมน์ ความกว้าง — **แก้ฟอร์มที่นี่ที่เดียว** |
| `transferRequest.ts` | วาดออกมาเป็นไฟล์ Word |
| `transferRequestPdf.ts` | วาดออกมาเป็นไฟล์ PDF |

ทั้งสองตัววาดอ่านเนื้อหาจากไฟล์เดียวกัน เอกสารสองแบบจึงไม่หลุดจากกัน

ไม่ได้เติมค่าลงไฟล์แม่แบบ เพราะแม่แบบวางช่องกรอกด้วย tab พอเติมข้อความยาวไม่เท่ากัน
คอลัมน์ขวาจะเลื่อน และตารางในแม่แบบตายตัวที่ 4 บรรทัด

**ฟอนต์ของ PDF** — PDF ต้องฝังฟอนต์ไว้ในไฟล์ ไม่งั้นภาษาไทยจะหายทั้งหน้า
จึงมี Sarabun (สัญญาอนุญาต SIL OFL) อยู่ที่ `backend/assets/fonts/` พร้อมไฟล์สัญญาอนุญาต
เส้นทางที่โค้ดใช้อ้างอิงจาก `__dirname` ซึ่งชี้ไปที่เดียวกันทั้งตอน dev และตอนรันจาก `dist/`
จึงไม่ต้องมีขั้นตอนก๊อปไฟล์ตอน build

### นำเข้าอะไหล่จากไฟล์ Excel

```bash
cd backend

# 1) ตรวจสอบก่อน (ยังไม่บันทึกลงฐานข้อมูล)
npm run import:parts -- "C:\path\to\parts.xlsx"

# 2) ถ้าข้อมูลถูกต้องแล้ว บันทึกจริง
npm run import:parts -- "C:\path\to\parts.xlsx" --yes

# ใส่หลายไฟล์ในคำสั่งเดียวก็ได้ จะสรุปยอดรวมให้ตอนจบ
npm run import:parts -- "ไฟล์1.xlsx" "ไฟล์2.xlsx" "ไฟล์3.xlsx" --yes
```

ถ้าไฟล์ใดหาคอลัมน์ที่จำเป็นไม่เจอ จะข้ามเฉพาะไฟล์นั้นพร้อมแจ้งเตือน ไฟล์ที่เหลือยังนำเข้าตามปกติ

สคริปต์จะอ่านหัวตารางแถวแรกแล้วจับคู่คอลัมน์ให้อัตโนมัติ รองรับทั้งหัวตารางไทยและอังกฤษ
เช่น `รหัสสินค้า` `ชื่อรวม (ไทย)` `ยี่ห้อสินค้า` `Category` `รูปภาพประกอบ`
คอลัมน์ลำดับที่ (`ลำดับ`, `No.`) จะถูกข้ามโดยอัตโนมัติ

| ฟิลด์ | หัวตารางที่รองรับ (บางส่วน) | บังคับ |
|---|---|---|
| `partCode` | รหัสสินค้า, รหัสอะไหล่, Part Code, SKU | ✅ |
| `name` | ชื่อรวม, ชื่อสินค้า, ชื่ออะไหล่, Name | ✅ |
| `brand` | ยี่ห้อสินค้า, ยี่ห้อ, แบรนด์, Brand | |
| `category` | หมวดหมู่, ประเภท, Category | |
| `description` | รายละเอียด, หมายเหตุ, Description | |
| `imageUrl` | รูปภาพประกอบ, รูปภาพ, Image | |

**รูปภาพ** นำเข้าได้ 3 แบบ:
1. **รูปที่วางในเซลล์** (Excel: Insert → Picture → Place in Cell) — ดึงออกมาให้อัตโนมัติ ไม่ต้องทำอะไรเพิ่ม
2. **ลิงก์ URL** ในคอลัมน์รูปภาพ — เก็บลิงก์ไว้ตรงๆ
3. **โฟลเดอร์รูป** — ตั้งชื่อไฟล์ตามรหัสสินค้า (`SPOS0002.jpg`) แล้วเพิ่ม `--images ./photos`

การนำเข้าใช้รหัสสินค้าเป็นตัวเทียบ — รหัสที่มีอยู่แล้วจะถูก**อัปเดต** รหัสใหม่จะถูก**เพิ่ม**
และจะ**ไม่ลบ**ข้อมูลเดิมทิ้ง จึงรันซ้ำได้อย่างปลอดภัย

### นำเข้าผังวินิจฉัยจาก Excel

ผังแก้ปัญหาของผู้ผลิตมักวาดเป็น flowchart ใน Excel (กล่องคำถาม + ลูกศร + ป้ายใช่/ไม่)
สคริปต์จะอ่านผังนั้นแล้วประกอบกลับเป็นต้นไม้ตัดสินใจที่กดตอบทีละขั้นได้ในแอป

```bash
cd backend

# 1) ดูผังที่ประกอบได้ ก่อนบันทึกอะไร
npm run preview:flow -- "C:\path\DryerTroubleshoot.xlsx"

# ดูรายละเอียดเป็นต้นไม้ทีละหัวข้อ
npm run preview:flow -- "C:\path\DryerTroubleshoot.xlsx" --topic 2

# 2) บันทึกจริง
npm run import:flow -- "C:\path\DryerTroubleshoot.xlsx" --yes --machine "เครื่องอบผ้า"
```

**ข้อจำกัดสำคัญ:** Excel ไม่ได้เก็บว่าลูกศรเส้นไหนเชื่อมกล่องไหน (ไม่มี `stCxn`/`endCxn`)
สคริปต์จึงต้องประกอบผังกลับจาก**พิกัดของกล่องและลูกศร** ซึ่งได้ผลราว **80%** ของคำถาม
ส่วนที่เหลือจะถูกนำเข้าโดยเว้นเส้นทางไว้ว่าง แล้ว:

- แอปจะขึ้นป้าย "⚠ ยังไม่สมบูรณ์" ที่หัวข้อนั้น และบอกช่างตรงจุดที่ผังขาด — **ไม่เดาเส้นทางให้**
- แอดมินเข้าไปเติมได้ที่เมนู **ตรวจสอบผังวินิจฉัย** (เลือกกล่องปลายทางจากรายการ)

บางจุดที่ปลายลูกศรหยุดห่างจากกล่องเล็กน้อย สคริปต์จะจับคู่ให้แบบผ่อนเกณฑ์ (เฉพาะเมื่อมีลูกศร
เหลือเส้นเดียวที่เข้าเค้า) และรายงานจำนวนไว้ในโหมดตรวจสอบ — จุดพวกนี้ควรสุ่มตรวจกับต้นฉบับ

ดูสาเหตุที่ประกอบไม่ได้รายจุดด้วย:
```bash
npx ts-node scripts/diagnose-flowchart.ts "C:\path\DryerTroubleshoot.xlsx"
```

เนื่องจากเป็นงานไฟฟ้าแรงสูง ควรตรวจผังให้ครบก่อนให้ช่างใช้งานจริง

รูปแผนผังวงจรที่ฝังในไฟล์ Excel จะถูกนำเข้าอัตโนมัติ และแตะดูแบบขยาย/ซูมได้ในแอป

### Endpoints หลัก

**Auth**
- `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`

**เครื่องซัก/อบ**
- `GET /api/machines/outages?ownership=&grade=&region=&zone=&search=&breachedOnly=&workStatus=` — เครื่องดับ รายเครื่อง
  (`workStatus=NONE` = เฉพาะเคสที่ยังไม่มีใครกรอกสถานะ · `search` ค้นยี่ห้อและอาการด้วย)
- `GET /api/machines/signal-lost?...` — สาขาสัญญาณหาย รายสาขา
- `GET /api/machines/work-statuses` — ตัวเลือกสถานะการดำเนินการ (value + ป้ายภาษาไทย)
- `GET /api/machines/regions?kind=&ownership=` — ภาคที่มีเคสค้างอยู่ พร้อมจำนวนเคสและจำนวนสาขา
  ใช้ทำแถบกรองภาค (`region=NONE` ในการค้นหา = สาขาที่ยังไม่มีภาคในทะเบียน)
- `PATCH /api/machines/outages/:id/note` — ส่ง `{ symptom, workStatus, parts }` บันทึกอาการ สถานะ
  และอะไหล่ที่รอของเคส (ผู้ใช้ที่ล็อกอินแล้วทุกคน · ส่ง `null` เพื่อล้างค่า)
  `parts` เป็น `[{ sparePartId, quantity }]` และ**แทนที่ของเดิมทั้งชุด** ส่ง `[]` คือล้างออกให้หมด
  ส่ง `scheduledVisitAt` เป็น `"YYYY-MM-DD"` เพื่อบันทึกวันที่ช่างนัดเข้า
- `GET /api/machines/outages/:id/note-logs` — ประวัติการกรอกของเคสเดียว เก่าสุดก่อน
- `GET /api/machines/note-logs?limit=` — ประวัติการกรอกล่าสุดของทุกเคสรวมกัน ใหม่สุดก่อน
- `GET /api/machines/score-history?groupBy=none|region|zone|ownership&kind=&days=` — คะแนนย้อนหลัง
  จาก snapshot ที่ตรึงไว้ทุกรอบอัปโหลด ได้จุดต่อรอบพร้อมคะแนน จำนวนเคส จำนวนสาขา และจำนวนที่เลย SLA
- `GET /api/machines/waiting-parts` — อะไหล่ที่ค้างอยู่ทั้งหมด รวมยอดข้ามสาขา
  ได้ `partCode`, `totalQuantity`, `caseCount` และรายชื่อรหัสสาขาที่รออยู่
- `GET /api/machines/overview` — ตัวเลขรวมของทั้งสองแท็บ + ข้อมูลการอัปโหลดครั้งล่าสุด

**ใบงานซ่อม**
- `GET /api/work-orders?status=ACTIVE|OPEN|IN_PROGRESS|DONE|CANCELLED|ALL&assignedTo=me&search=`
  รายการใบงาน เรียงด่วนก่อนแล้วเก่าก่อน พร้อมยอดแยกตามสถานะ
- `GET /api/work-orders/options` — ตัวเลือกสถานะ ความเร่งด่วน ผลงาน และรายชื่อช่าง
- `GET /api/work-orders/:id` — ใบงานหนึ่งใบ พร้อมประวัติทั้งหมด
- `POST /api/work-orders` — เปิดเอง ส่ง `{ branchCode, machineCode?, title, detail?, priority?, assignedToId?, scheduledAt?, symptom?, workStatus?, waitingParts? }`
- `POST /api/work-orders/from-outage/:outageId` — เปิดจากเคสบนกระดาน
  (ตอบ `409` พร้อมใบงานเดิม ถ้าเคสนั้นมีใบงานเปิดค้างอยู่แล้ว)
- `PATCH /api/work-orders/:id` — แก้เนื้อความ ความเร่งด่วน หรืออาการ/สถานะ
  (`symptom`, `workStatus`, `waitingParts`) ซึ่งจะถูกส่งต่อไปที่เคสให้เอง — ไม่ใช้เดินขั้น
- `POST /api/work-orders/:id/parts` — ขั้น 2 หัวหน้าภาคตัดสินเรื่องอะไหล่
  `{ needsParts, parts?, note? }` — `needsParts=false` ข้ามขั้น 3 ไปที่ `PARTS_CHECKED` เลย
- `POST /api/work-orders/:id/reassess-parts` — ช่างส่งกลับไปขั้น 1 `{ reason, parts? }`
  (บังคับใส่เหตุผล · `parts` คืออะไหล่ที่ช่างขอเบิกเพิ่ม ใส่แล้ว `needsParts` เป็น true ให้เอง)
- `POST /api/work-orders/:id/parts-check` — ขั้น 3 แอดมินเช็คคลัง
  `{ results: [{ sparePartId, inStock, warehouse? }], note? }` (ต้องครบทุกตัว)
- `POST /api/work-orders/:id/assign` — ขั้น 4 หัวหน้าภาคจ่ายงาน `{ assignedToId, note? }`
- `POST /api/work-orders/:id/schedule` — ขั้น 5 ช่างนัดวัน `{ scheduledAt, note? }`

ทุกขั้นตอบ `409` ถ้าใบงานยังไม่ถึงขั้นนั้น และ `403` ถ้าคนกดไม่ใช่เจ้าของขั้น
หรือเป็นหัวหน้าภาคคนละภาค

**ผู้ใช้**
- `POST /api/auth/users` — แอดมินสร้างบัญชี `{ employeeCode, name, phone?, role, region?, password }`
- `POST /api/auth/users/:id/reset-password` — แอดมินตั้งรหัสใหม่ให้ `{ password }`
- `POST /api/auth/change-password` — เจ้าของบัญชีเปลี่ยนเอง `{ currentPassword, newPassword }`
  → คืนโทเคนใบใหม่ที่ไม่มีธงบังคับเปลี่ยนแล้ว
- `GET /api/branches/regions` — ภาคทั้งหมดจากทะเบียนสาขา ใช้ตอนตั้งภาคให้หัวหน้าภาค
- `GET /api/work-orders/inbox-count` — จำนวนใบงานที่รอคนที่ถามมา ใช้กับตัวเลขบนเมนูหน้าแรก
  (แยกจาก `/work-orders` เพราะหน้าแรกอยากได้แค่ตัวเลข ไม่ได้อยากได้รายการ)
- `GET /api/branches/:code/machines` — เครื่องของสาขานี้พร้อมรุ่นกับขนาดที่เคยกรอกไว้
  ใช้เติมให้ในฟอร์มเปิดใบงาน (เครื่องที่ถอดออกแล้วไม่ส่งมา)
- `GET /api/branches/teams` — ทีมช่างทั้งหมดจากทะเบียนสาขา (คอลัมน์ `ทีมช่าง`)
  พร้อมจำนวนสาขาที่แต่ละทีมดูแล ใช้ตอนจ่ายงานและตอนจัดทีมให้ช่าง
- `GET /health/db` — เวลาไปกลับฐานข้อมูลหนึ่งรอบ ใช้หาสาเหตุเวลาบันทึกช้า (แอดมิน)
- `GET /health/storage` — ที่เก็บไฟล์ต่อได้จริงไหม บอกว่าพังขั้นไหน (แอดมิน)
- `GET /api/auth/users` — รายชื่อผู้ใช้พร้อมสิทธิ์และภาค (แอดมิน)
- `PATCH /api/auth/users/:id` — ตั้งสิทธิ์และภาค `{ role?, region? }` (แอดมิน
  · ลดสิทธิ์แอดมินคนสุดท้ายไม่ได้)
- `POST /api/work-orders/:id/close` — ปิดงาน ส่ง `{ result, note?, parts? }`
- `POST /api/work-orders/:id/cancel` — ยกเลิกใบงาน
- `POST /api/work-orders/:id/reopen` — เปิดใหม่ (แอดมินเท่านั้น) เผื่อปิดผิดใบ
- `DELETE /api/work-orders/:id` — ลบถาวร (แอดมินเท่านั้น) สำหรับใบที่เปิดผิดหรือเปิดซ้ำ

## แอป (ใช้ได้ทั้งมือถือและคอมพิวเตอร์)

โค้ดชุดเดียวกันรันได้ทั้งบนมือถือ (React Native) และบนเบราว์เซอร์ (react-native-web)

```bash
cd mobile
cp .env.example .env       # ตั้งค่า EXPO_PUBLIC_API_URL ให้ชี้ไปที่ backend
npm install

npx expo start             # มือถือ: สแกน QR ด้วยแอป Expo Go
npx expo start --web       # คอม: เปิดในเบราว์เซอร์
```

บนคอมจะจำกัดความกว้างเนื้อหาไว้ให้อ่านง่าย ไม่ยืดเต็มจอ ส่วนบนมือถือแสดงเต็มจอเหมือนเดิม

**การตั้งค่า `EXPO_PUBLIC_API_URL`:**
- ถ้า deploy backend แล้ว ใช้ URL จริง เช่น `https://service-app-xxxx.onrender.com`
- ถ้ารัน backend ในเครื่อง ใช้ IP แบบ LAN เช่น `http://192.168.1.20:4000` (ไม่ใช่ `localhost`
  เพราะมือถือเป็นคนละเครื่อง) และมือถือต้องอยู่ Wi-Fi วงเดียวกัน

หลังแก้ `.env` ทุกครั้งต้องปิด Expo (Ctrl+C) แล้วรัน `npx expo start` ใหม่

## การ Deploy

**Backend (Render free tier):**
- Root Directory: `backend`
- Build Command: `npm install && npm run build`
- Start Command: `npm run start:prod` — **ควรเปลี่ยนมาใช้อันนี้** ของเดิมคือ
  `npx prisma migrate deploy && npm run start` ซึ่งทำให้ deploy ล้มเมื่อ pooler เต็ม
  (ดู "deploy ล้มเพราะ pooler เต็ม" ด้านล่าง)
- Environment Variables: `DATABASE_URL`, `DIRECT_URL`, `JWT_SECRET` (ใส่ค่าเปล่าๆ ไม่ต้องมีเครื่องหมาย `"`)
  และค่า `STORAGE_*` ถ้าจะให้ช่างแนบรูปในใบงานได้
- ห้ามตั้ง `PORT` เอง — Render กำหนดให้อัตโนมัติ

#### `npx prisma` ใน Start Command — เคยเป็นกับดัก ตอนนี้ปิดแล้ว

Start Command ที่ตั้งอยู่บน Render คือ `npx prisma migrate deploy && npm run start`
ซึ่งเคยเป็นกับดักที่ทำให้ deploy พังเองได้โดยไม่มีใครแก้โค้ด — แต่ปิดไปแล้ว
**ไม่ต้องแก้ Start Command** ขอบันทึกไว้ให้ครบ เพราะถ้าเผลอย้าย `prisma` กลับ
ไป `devDependencies` วันหนึ่ง กับดักจะกลับมาทันทีโดยไม่มีอะไรเตือน

**กับดักคืออะไร** `npx` ไม่ได้ผูกเวอร์ชันไว้ — **ถ้าหา binary ในเครื่องไม่เจอ**
มันจะไปโหลด `prisma` ตัว `latest` จาก npm มาใช้ ซึ่งวันหนึ่งจะไม่ใช่เวอร์ชันเดียว
กับโปรเจกต์ (ตรวจเมื่อ 2 ต.ค. 2569: โปรเจกต์ใช้ **5.22.0** ส่วน `latest` คือ
**8.0.0-rc.19** ซึ่งเปลี่ยนทั้งรูปแบบคำสั่งและผลลัพธ์) และเพราะมี `&&` อยู่
migrate ที่ล้มเหลวจะตัดไม่ให้เซิร์ฟเวอร์สตาร์ทเลย แอปขึ้นว่า
"เชื่อมต่อเซิร์ฟเวอร์ไม่ได้" ซึ่งดูเหมือนปัญหาเน็ตทั้งที่เป็นปัญหา migrate

**ทำไมเคยหาไม่เจอ** `prisma` อยู่ใน `devDependencies` และ Render ตั้ง
`NODE_ENV=production` ให้เอง ซึ่งทำให้ `npm install` ข้าม devDependencies ทั้งก้อน
ตอน runtime จึงไม่มี binary ให้ `npx` ใช้ — เงื่อนไขเดียวที่มันจะออกไปโหลดของใหม่

**ปิดด้วยการย้าย `prisma` ไป `dependencies`** binary จึงอยู่ติดเครื่องทุก deploy
และ `npx` หาในโปรเจกต์ก่อนเสมอ ไม่ได้ออกเน็ต ตรวจได้ด้วย `npx prisma --version`
บนเครื่องที่ติดตั้งแล้ว ต้องขึ้น 5.22.0 ไม่ใช่เวอร์ชัน 8

ที่แก้ตรงนี้ **ไม่ใช่** Start Command เพราะกับดักอยู่ที่ว่า binary มีให้หาไหม
ไม่ได้อยู่ที่ว่าใครเป็นคนเรียก — แก้ที่ `package.json` จึงปิดได้ทั้งคนที่เรียกด้วย
`npx` และคนที่เรียกด้วย `npm run` พร้อมกัน และไม่ต้องพึ่งว่าใครจำไปตั้งค่าบน Render

ยังเหลือข้อต่างอยู่ข้อเดียว เป็นเรื่อง "พังแล้วรู้เร็วแค่ไหน" ไม่ใช่เรื่องถูกผิด:
ถ้าวันหนึ่ง `node_modules/.bin/prisma` หายไปด้วยเหตุอะไรก็ตาม `npx` จะเงียบ ๆ
ไปโหลดตัวใหม่มาใช้แทน ส่วน `npm run start:prod` (= `prisma migrate deploy &&
node dist/index.js`) จะพังดัง ๆ ให้เห็นทันที ไว้วันไหนเข้าไปแก้ค่าอื่นบน Render
อยู่แล้วค่อยเปลี่ยนก็ได้

การกั้นเซิร์ฟเวอร์ไว้หลัง migrate ยังถูกต้องอยู่ — โค้ดใหม่ที่วิ่งบนฐานข้อมูลเก่า
แย่กว่าเซิร์ฟเวอร์ที่ไม่ขึ้น เพราะอย่างหลังรู้ทันที

Render free tier จะพักเซิร์ฟเวอร์เมื่อไม่มีคนใช้งาน ครั้งแรกที่เรียกอาจช้า 30-60 วินาที

#### deploy ล้มเพราะ pooler เต็ม (EMAXCONNSESSION)

อาการใน Logs ของ Render:

```
Running 'npx prisma migrate deploy && npm run start'
Error: Schema engine error:
FATAL: (EMAXCONNSESSION) max clients reached in session mode - max clients are limited to pool_size: 15
==> Exited with status 1
```

**ไม่ใช่ migration ผิด แต่ต่อฐานข้อมูลไม่ติด** session pooler ของ Supabase รับได้
15 client พร้อมกัน ส่วน Prisma เปิด connection ตามจำนวน CPU (ปกติ 9 ต่อ instance)
ตอน deploy ตัวเก่ายังไม่ตายแต่ตัวใหม่ขึ้นมาแล้ว จึงมีสองชุดพร้อมกัน = 18 เกินโควตา

**ทุก deploy จึงมีสิทธิ์ล้มแบบนี้ ไม่ใช่เรื่องบังเอิญ** และเพราะมี `&&` คั่น
migrate ที่ล้มจะตัดไม่ให้เซิร์ฟเวอร์สตาร์ทเลย แอปทั้งระบบขึ้นว่า
"เชื่อมต่อเซิร์ฟเวอร์ไม่ได้" ทั้งที่โค้ดไม่มีอะไรผิด

แก้สองชั้น:

1. **ใส่ `connection_limit` ใน Environment Variables ของ Render**
   - `DATABASE_URL` ลงท้ายด้วย `?connection_limit=5` (ถ้ามี `?` อยู่แล้วใช้ `&`)
   - `DIRECT_URL` ลงท้ายด้วย `?connection_limit=1` — migrate ใช้เส้นเดียวพอ

   ห้าเส้นพอสำหรับงานจริง และสอง instance ซ้อนกันก็ยังแค่ 10 จาก 15

2. **ตั้ง Start Command เป็น `npm run start:prod`** ซึ่งตอนนี้เรียก
   `scripts/start-prod.js` ที่
   - บังคับ `connection_limit=1` ตอน migrate ให้เอง ไม่ต้องรอใครไปตั้ง
   - **ลองใหม่ถึง 6 ครั้ง** (5·10·20·30·30 วินาที) เมื่อเป็นปัญหาการต่อ —
     ช่วงที่ตัวเก่าปล่อย connection ใช้เวลาไม่กี่สิบวินาที รอแล้วลองใหม่ก็ผ่าน
   - **ไม่ลองใหม่** เมื่อเป็นความผิดพลาดที่ลองกี่ครั้งก็ไม่หาย เช่นรหัสผ่านผิด
     หรือ migration ชนกัน — ตายทันทีใน 1 วินาที ไม่วนให้เสียเวลา
   - ยังกั้นเซิร์ฟเวอร์ไว้หลัง migrate เหมือนเดิม โค้ดใหม่บนฐานข้อมูลเก่า
     แย่กว่าเซิร์ฟเวอร์ที่ไม่ขึ้น

**ถ้าติดอยู่ตอนนี้และต้องการให้ขึ้นเดี๋ยวนี้** connection ที่ค้างมาจาก instance เก่า
กับรอบที่ crash ไปแล้ว — ปล่อยไว้สักสองสามนาทีแล้วกด Manual Deploy ใหม่
หรือเข้า Supabase → Database → Connection pooling ตัด connection ที่ค้างทิ้ง

#### แอปขึ้นว่า "เชื่อมต่อเซิร์ฟเวอร์ไม่ได้" — ไล่ตรงไหน

ข้อความนี้แปลว่า**ไม่ได้รับ HTTP response เลย** ไม่ใช่ error ที่ backend ส่งมา
ถ้า backend ขึ้นอยู่แต่มีปัญหา จะได้ข้อความจาก backend แทน

ไล่ตามลำดับนี้ เปิดจากเบราว์เซอร์ตรง ๆ:

| เปิด | ได้อะไร | แปลว่า |
|---|---|---|
| `<backend>/health` | `{"status":"ok"}` | เซิร์ฟเวอร์ขึ้นแล้ว ไปดูข้อถัดไป |
| `<backend>/health` | ไม่ตอบ / 502 / 503 | **เซิร์ฟเวอร์ไม่ขึ้น** — ไปอ่าน Logs ของ Render |
| `<backend>/health/db` | ช้ามากหรือค้าง | ต่อฐานข้อมูลไม่ได้ (ต้องล็อกอินแอดมินก่อน) |

`/health` ไม่แตะฐานข้อมูลเลย จึงตอบได้แม้ฐานข้อมูลล่ม — ใช้แยกว่า
"เซิร์ฟเวอร์ไม่ขึ้น" กับ "เซิร์ฟเวอร์ขึ้นแต่ต่อฐานข้อมูลไม่ได้" ออกจากกันได้

ถ้า `/health` ไม่ตอบ ให้ดู **Render → Logs** บรรทัดสุดท้ายก่อนเซิร์ฟเวอร์ตาย
สาเหตุที่เจอบ่อยคือ `prisma migrate deploy` ล้มเหลวแล้ว `&&` ตัดไม่ให้เซิร์ฟเวอร์สตาร์ท

**ถ้าพังเฉพาะบางปุ่ม ไม่ใช่ทั้งแอป** แปลว่าเซิร์ฟเวอร์ขึ้นอยู่ แต่คำขอนั้นพังข้างใน
สาเหตุที่เจอคือ **deploy โค้ดใหม่แต่ migration ยังไม่รัน** — โค้ดอ่านคอลัมน์ที่ยัง
ไม่มีในฐานข้อมูล เฉพาะปุ่มที่แตะคอลัมน์นั้นจึงพัง ส่วนที่เหลือยังใช้ได้ปกติ
เช็คได้จาก Logs ว่ามีบรรทัด `The column ... does not exist in the current database` ไหม
แก้ด้วยการ deploy ใหม่ให้ `prisma migrate deploy` ได้รัน

#### เพดาน 5 วินาทีของ transaction

Prisma ตั้งเพดานเวลาของ interactive transaction ไว้ **5 วินาที** ซึ่งพอสำหรับ
ฐานข้อมูลที่อยู่เครื่องเดียวกัน แต่ของจริงอยู่คนละ region — ทุกคำสั่งใน transaction
คือการเดินทางไปกลับจริง ๆ

ใบงานที่**เปิดจากกระดาน**แพงกว่าใบที่เปิดเองเกินเท่าตัว เพราะต้องคัดลอกค่าไปที่เคสด้วย:

| ใบงาน | รอบไปกลับใน transaction ตอนกดยืนยันอะไหล่ |
|---|---|
| เปิดเอง | 4 |
| เปิดจากกระดาน | 9 (เพิ่มการอัปเดตเคส อะไหล่ของเคส และประวัติของเคส) |

ไปกลับรอบละ 600 ms ก็ชนเพดานแล้ว และ transaction ที่ชนเพดานจะโยน `P2028`
ซึ่งก่อนหน้านี้ไม่มีใครรับ ผู้ใช้จึงเห็นเป็น "เชื่อมต่อเซิร์ฟเวอร์ไม่ได้"
**เฉพาะใบที่เปิดจากกระดาน** ส่วนใบที่เปิดเองใช้ได้ปกติ — อาการที่ดูเหมือนปัญหาเน็ต
แต่ที่จริงคือระยะทางไปฐานข้อมูล

ตอนนี้ transaction ที่เดินสายงานใบงานทุกตัวใช้ `STAGE_TX` (30 วินาที) เท่ากับที่
ขั้นเปิดใบงานใช้อยู่แล้ว — ไม่ได้แปลว่ายอมให้ช้าได้ขนาดนั้น แต่แปลว่าเน็ตสะดุด
ชั่วคราวไม่ควรกลายเป็นงานที่บันทึกไม่ได้

วัดระยะทางไปฐานข้อมูลได้ที่ `GET /health/db` (`roundTripMs`) — เอา 9 คูณดู
ถ้าใกล้ 5000 ms แปลว่าเคยชนเพดานมาแล้ว

#### ทำไมคำขอที่พังเคยเงียบสนิท

Express 4 ไม่รู้จัก promise ที่ reject — handler ที่เป็น `async` แล้ว throw ข้างใน
จะไม่มีใครตอบคำขอนั้นเลย คำขอค้างจนฝั่งแอปหมดเวลา แล้วแอปขึ้นว่า
"เชื่อมต่อเซิร์ฟเวอร์ไม่ได้" ทั้งที่เซิร์ฟเวอร์ยังอยู่ดี และรู้ด้วยซ้ำว่าพังเพราะอะไร
อาการจึงชี้ไปผิดที่ทั้งหมด — ไปไล่เรื่องเน็ตและ Render ทั้งที่ปัญหาอยู่ที่ฐานข้อมูล

ปิดช่องนี้ด้วย `express-async-errors` (import ไว้บนสุดของ `src/index.ts`
ก่อนสร้าง app เพราะมันแพตช์ Router ตอนโหลด) คู่กับ error middleware ท้ายไฟล์
ที่ตอบ 500 พร้อมข้อความไทย และเขียน error จริงลง log

ข้อความที่ส่งกลับไปไม่มีรายละเอียดของ error เพราะมันบอกชื่อตารางและชื่อคอลัมน์
ให้คนที่ไม่ควรรู้ ส่วนใน log เขียนไว้ครบ

### ย้ายไปสิงคโปร์ทั้งคู่

ขั้นตอนละเอียดอยู่ที่ [`docs/migrate-singapore.md`](docs/migrate-singapore.md) —
แบ่งเป็นสองช่วง ช่วงแรกย้าย Render (ไม่แตะข้อมูล ย้อนได้ตลอด) ช่วงที่สองย้าย Supabase
(ขนข้อมูลจริง ต้องมีช่วงปิดระบบ) พร้อมวิธีย้อนกลับของแต่ละช่วง

**ย้ายก่อนตั้ง Storage** — ตราบใดที่ยังไม่มีไฟล์รูปในระบบ การย้ายคือการขนแค่ฐานข้อมูล
ถ้าตั้ง Storage แล้วช่างเริ่มอัปรูป จะต้องขนไฟล์ตามไปอีกชุด

### ย้าย backend ไปอยู่ region เดียวกับฐานข้อมูล

เหตุผลเดียวที่ต้องย้ายคือ**ระยะทางระหว่างเซิร์ฟเวอร์กับฐานข้อมูล** การเปิดใบงาน
หนึ่งใบคุยกับฐานข้อมูลประมาณ 13 รอบ ถ้าอยู่คนละทวีปกันที่ 200 ms ต่อรอบ
คือรอเกือบสามวินาทีทุกครั้งที่กดบันทึก โดยที่โค้ดไม่ได้ผิดอะไรเลย

เช็คก่อนว่าจำเป็นจริงไหมด้วย `GET /health/db` (ดูหัวข้อ "เวลากดบันทึกแล้วช้า")
ถ้าได้ต่ำกว่า 30 ms อยู่แล้ว ไม่ต้องย้าย

`backend/Dockerfile` รันได้ทุกที่ที่รับ Dockerfile — Fly.io, Railway, Koyeb,
DigitalOcean หรือแม้แต่ Render เอง **ไม่มีอะไรในโค้ดผูกกับผู้ให้บริการรายไหน**

#### Fly.io (เลือก region ได้ละเอียดที่สุด)

`backend/fly.toml` เตรียมไว้แล้ว แก้ `primary_region` ให้ตรงกับ region ของ Supabase
(ดูที่ Project Settings → General)

| Supabase | Fly |
|---|---|
| Singapore `ap-southeast-1` | `sin` |
| Tokyo `ap-northeast-1` | `nrt` |
| Sydney `ap-southeast-2` | `syd` |
| Frankfurt `eu-central-1` | `fra` |
| Virginia `us-east-1` | `iad` |

```bash
cd backend
fly launch --no-deploy        # ใช้ fly.toml ที่มีอยู่ อย่าให้มันเขียนทับ
fly secrets set \
  DATABASE_URL="..." DIRECT_URL="..." JWT_SECRET="..." \
  STORAGE_ENDPOINT="..." STORAGE_REGION="..." \
  STORAGE_ACCESS_KEY_ID="..." STORAGE_SECRET_ACCESS_KEY="..." \
  STORAGE_BUCKET="service-app"
fly deploy
```

**อย่าเปลี่ยน `auto_stop_machines = false` กับ `min_machines_running = 1`** ใน `fly.toml`
— Fly ปิดเครื่องเองตอนไม่มีคนใช้ถ้าเปิดค่านั้น ซึ่งจะได้อาการเดียวกับที่หนีมาจาก Render เป๊ะ ๆ

#### Railway (ย้ายง่ายที่สุด)

ต่อ GitHub แล้วตั้ง Root Directory เป็น `backend` — Railway เห็น Dockerfile แล้วใช้เอง
ไม่ต้องมีไฟล์ตั้งค่าเพิ่ม เลือก region ตอนสร้าง service และใส่ตัวแปรชุดเดียวกับข้างบน

#### หลังย้ายเสร็จ ต้องทำอีกสองอย่าง

1. **แก้ `EXPO_PUBLIC_API_URL` ให้เป็น URL ใหม่ แล้ว build เว็บใหม่**
   (Clear build cache & deploy) — ค่านี้ถูกฝังลงไฟล์ตอน build ไม่ได้อ่านตอนเปิดหน้า
   ถ้าลืม เว็บจะยังยิงไปที่ Render ตัวเก่า
2. **เปิด `GET /health/db` ด้วยบัญชีแอดมิน** ยืนยันว่าตัวเลขลดลงจริง ถ้ายังสูงอยู่
   แปลว่า region ที่เลือกยังไม่ตรงกับฐานข้อมูล

หน้าเว็บ (static site) ไม่ต้องย้ายก็ได้ — เป็นไฟล์นิ่ง ไม่มีเรื่อง region เข้ามาเกี่ยว
ถ้าจะย้ายด้วย Cloudflare Pages กับ Netlify ฟรีทั้งคู่ ตั้งค่าเหมือนกับที่ตั้งบน Render

**เว็บ — วิธีที่แนะนำ ใช้ได้ทั้งคอมและมือถือ ไม่ต้องเปิดคอมทิ้งไว้**

deploy เป็นเว็บ static แล้วช่างเปิดจากลิงก์ได้เลย ไม่ต้องติดตั้งแอป ไม่ต้องมี Expo Go

**ตั้งค่าบน Render (Static Site):**

| ช่อง | ค่าที่ใส่ |
|---|---|
| Root Directory | `mobile` |
| Build Command | `npm install && npm run build:web` |
| Publish Directory | `dist` |
| Environment Variable | `EXPO_PUBLIC_API_URL` = URL ของ backend เช่น `https://service-app-xxxx.onrender.com` |

#### เช็คว่าเว็บที่เปิดอยู่เป็นรุ่นไหน

ท้ายหน้าแรกของแอปมีบรรทัดเล็กๆ บอกรุ่น เช่น `รุ่น 93fc6fb · build 26 ส.ค. 2569 14:02`
ค่านี้ถูกเขียนตอน build ไม่ใช่ตอนเปิดหน้า

**แก้โค้ดแล้วของใหม่ไม่ขึ้น ให้ดูบรรทัดนี้ก่อน** ถ้ารหัสยังเป็นรุ่นเก่า แปลว่ายังไม่ได้
deploy ใหม่ ไม่ใช่โค้ดไม่ทำงาน — สองอย่างนี้ดูจากหน้าจอเฉยๆ แยกไม่ออก

**backend กับเว็บ deploy แยกกัน** แก้ฝั่งหน้าจอแล้ว deploy แต่ backend หน้าจอจะไม่เปลี่ยน
ต้อง deploy static site ด้วยเสมอ

**ห้ามลืม `EXPO_PUBLIC_API_URL`** — ค่านี้ถูกฝังลงในไฟล์ตอน build ถ้าไม่ตั้ง แอปจะพยายามต่อ
`localhost` แล้วใช้งานไม่ได้ (กรณีนี้แอปจะขึ้นข้อความบอกสาเหตุให้ ไม่ปล่อยให้งง)
แก้ค่านี้ทีหลังต้องกด **Manual Deploy → Clear build cache & deploy** ให้ build ใหม่

ใช้ Netlify / Vercel / Cloudflare Pages ก็ได้ ตั้งค่าเหมือนกัน (ไฟล์ `mobile/public/_redirects`
มีกฎ SPA rewrite ไว้ให้แล้ว)

build เองในเครื่องก็ได้ ถ้าอยากเอาไฟล์ไปวางเอง:

```bash
cd mobile
EXPO_PUBLIC_API_URL="https://service-app-xxxx.onrender.com" npm run build:web
# ได้โฟลเดอร์ dist/ เป็นไฟล์ static
```

**ข้อควรรู้:** backend บน Render free tier จะหลับเมื่อไม่มีคนใช้ ครั้งแรกของวันที่เปิดแอป
อาจรอ 30-60 วินาที ครั้งต่อๆ ไปเร็วปกติ

**Mobile (ไฟล์ APK ติดตั้งบนมือถือ):**

ระหว่างพัฒนา แอปรันผ่าน `npx expo start` ซึ่งต้องเปิดคอมค้างไว้ตลอด
ถ้าต้องการให้ช่างใช้งานได้โดยไม่ต้องพึ่งคอม ให้ build เป็น APK:

```bash
cd mobile
# แก้ EXPO_PUBLIC_API_URL ใน eas.json ให้เป็น URL จริงของ Render ก่อน
npx eas build --platform android --profile preview
```

**สำคัญ:** ต้องแก้ `EXPO_PUBLIC_API_URL` ใน `eas.json` ก่อน build เพราะค่านี้ถูกฝังลงในแอปตอน build
ไฟล์ `.env` ในเครื่องไม่ถูกส่งขึ้น EAS (อยู่ใน .gitignore) แอปที่ได้จึงจะหา backend ไม่เจอถ้าไม่ตั้งค่าตรงนี้

เมื่อ build เสร็จ EAS จะให้ลิงก์ดาวน์โหลด APK ส่งให้ช่างติดตั้งได้เลย ไม่ต้องลง Expo Go

แก้โค้ดภายหลังแล้วส่งอัปเดตเข้าแอปที่ติดตั้งไว้แล้วได้โดยไม่ต้อง build ใหม่:

```bash
npx eas update --branch preview
```

## หมายเหตุด้านความปลอดภัย

- รหัสผ่านถูกเข้ารหัสด้วย bcrypt ก่อนบันทึกลงฐานข้อมูล
- Token เป็น JWT อายุ 30 วัน ต้องเปลี่ยน `JWT_SECRET` ก่อนใช้งานจริง
- รูปอะไหล่เก็บเป็น binary ในฐานข้อมูล และ endpoint รูปเปิดสาธารณะเพื่อให้แอปโหลดรูปได้ตรง
  หากรูปอะไหล่ถือเป็นข้อมูลลับ ควรเพิ่มการตรวจสอบ token ที่ endpoint นี้
- คีย์ของที่เก็บไฟล์ (`STORAGE_*`) ต้องอยู่ที่ backend เท่านั้น ห้ามใส่ใน `mobile/.env` เพราะค่า
  `EXPO_PUBLIC_*` ถูกฝังลงในไฟล์ตอน build ใครเปิดเว็บก็อ่านได้
