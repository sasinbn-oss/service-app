# เทสต์

เทสต์ที่นี่ยิงไปที่ **backend ที่รันอยู่จริง** ไม่ใช่ unit test ที่ mock ทุกอย่าง
เพราะของที่เคยพังจริงในโปรเจกต์นี้คือเรื่องที่ unit test จับไม่ได้ — ลำดับขั้นของงาน
สิทธิ์ของแต่ละตำแหน่ง การเขียนทับข้อมูลข้ามรอบ และเวลาไปกลับฐานข้อมูล

**รันกับฐานข้อมูลสำหรับพัฒนาเท่านั้น** เทสต์เปิดใบงานจริง อัปโหลดไฟล์จริง
และแก้ภาค/ทีมของผู้ใช้ทดสอบ อย่าชี้ไปที่ฐานข้อมูลของจริงเด็ดขาด

## เตรียมก่อนรัน

ต้องมีสามอย่างรันอยู่: ฐานข้อมูล · ที่เก็บไฟล์จำลอง · backend

```bash
# 1) ที่เก็บไฟล์จำลอง (แทน Supabase Storage) — ค้างไว้อีกหน้าต่าง
node tests/mock-s3.js

# 2) backend ที่ชี้ไปที่ที่เก็บไฟล์จำลอง — ค้างไว้อีกหน้าต่าง
cd backend
STORAGE_ENDPOINT=http://localhost:9100 STORAGE_REGION=us-east-1 \
STORAGE_ACCESS_KEY_ID=dev STORAGE_SECRET_ACCESS_KEY=devsecret \
STORAGE_BUCKET=service-app npm run dev
```

**ครั้งแรกต้องเตรียมข้อมูลที่เทสต์ใช้ก่อน** รันซ้ำได้ ไม่ลบอะไรที่มีอยู่:

```bash
cd backend && npm run seed:test
```

สร้างให้: ผู้ใช้ `A001` (แอดมิน) `S001` (หัวหน้าภาค) `T001` (ช่าง) รหัสผ่าน `test1234`
· สาขา `C0001` `C0006` (บริษัท) `D0011` `D0012` (แฟรนไชส์ คนละฝั่งของเส้นประกัน 3 ปี)
· อะไหล่ `SP-BOARD` `SP-BELT` (ยี่ห้อ Oasis) กับตัวแฝดแยกยี่ห้อ `SP-BOARD-HB`/`SP-BELT-HB` (Huebsch) `-HA` (Haier) `-MT` (Maytag) `-OT` (Other)

**อะไหล่ที่เทสต์ส่งให้ใบงานต้องตรงยี่ห้อเครื่อง** — กฎ "เลือกอะไหล่ได้เฉพาะไฟล์ยี่ห้อเดียวกับเครื่อง" จะปฏิเสธอะไหล่ไม่มียี่ห้อ
และอะไหล่ต่างยี่ห้อจากทุกเส้นทาง ส่ง `SP-BOARD` ตัวเดียวให้ทุกเครื่องแบบเดิมจะพังทั้งที่แอปไม่ได้ผิด ให้ถามจาก helper:

```bash
. "$SP/lib/fixture-parts.sh"     # สคริปต์ API
PID=$(fx_part "$ID" BOARD)       # id อะไหล่ของใบ $ID (BOARD หรือ BELT) · fx_part_code ให้รหัสแทน
```
```js
const fx = await setup();        // เทสต์เบราว์เซอร์ (tests/browser/fixture.js) — เรียก fx_part ตัวเดียวกัน
const pid = fx.fxPart(id, "BOARD");
```

ยี่ห้อเครื่องอ่านจาก `brand` ก่อน ว่างแล้วใช้ `model` จับคำ huebsch/oasis/haier/maytag ไม่ตรงคำไหนเป็น Other — แบบเดียวกับแอป
ใบที่ไม่มีเครื่องได้ `SP-BOARD` · เครื่องที่ยังไม่รู้ยี่ห้อเลยถูกตั้ง `model='Haier'` ถาวร **ไม่ใช่ Oasis** เพราะ Haier
ได้ผลเหมือนไม่รู้ยี่ห้อทุกกฎที่ดูยี่ห้อ (ประกัน 3 ปี · ป้ายรุ่นแบบ OTHER) — ถ้าเป็น Oasis ประกันเหลือ 2 ปี
แล้วการเสนอราคา ป้ายประกัน และกฎเคลมของเครื่องทดสอบจะเปลี่ยนเอง ข้อตกลงเต็มอยู่หัวไฟล์ `tests/lib/fixture-parts.sh`
helper แก้ข้อมูลเครื่องได้ จึงปฏิเสธ `DATABASE_URL` บนคลาวด์แบบเดียวกับ `seed:test` และตรวจว่ามีอะไหล่ทดสอบครบห้ายี่ห้อก่อนเขียนอะไร
(ฐานที่ไม่เคยรัน `seed:test` ไม่ถูกแตะ) · ชุดที่ใช้อะไหล่ของตัวเอง (`branch-parts-report-test.sh`) ใส่ยี่ห้อ Haier ให้อะไหล่กับเครื่องเอง

เทสต์ส่วนใหญ่ถือว่า **S001 = ภาคใต้ภาคเดียว ไม่มีภาคเพิ่ม (`extraRegions` ว่าง)** แล้วสลับภาคด้วย SQL ที่ `region` อย่างเดียว
— ถ้า S001 ค้างภาคเพิ่มไว้ ข้อ "นอกพื้นที่ไม่เห็น" จะพังด้วยเหตุที่ไม่เกี่ยว `npm run seed:test` ล้าง `extraRegions` ของผู้ใช้ทดสอบให้
และเทสต์ที่ตั้งภาคเพิ่ม (`multi-region-test.sh`) คืนค่าใน trap
ทีมที่เพิ่มของ Senior ช่าง (`extraTeams`) ก็เหมือนกัน — `seed:test` ล้างให้ผู้ใช้ทดสอบ และ `senior-tech-test.sh` ใช้ผู้ใช้ `ZS…` ของตัวเอง ไม่ตั้ง T001 เป็น Senior

แยกจาก `prisma db seed` เพราะคนละเรื่อง — อันนั้นคือข้อมูลตัวอย่างของระบบจริง
ส่วนอันนี้คือฉากที่เทสต์ต้องการ ถ้าปนกันระบบจริงจะมีบัญชีรหัสผ่านง่าย ๆ ติดไปด้วย
และสคริปต์จะปฏิเสธถ้า `DATABASE_URL` ชี้ไปที่ฐานข้อมูลบนคลาวด์

**ตั้งภาคของหัวหน้าภาคให้ตรงกับสาขาที่ทดสอบตั้งแต่ต้นไฟล์** ก่อนเรียก API ใด ๆ
ไม่งั้นผลจะขึ้นกับว่าชุดก่อนหน้าทิ้งอะไรไว้ และรันเดี่ยว ๆ จะไม่ผ่าน

**อะไหล่ในสโตร์ที่ส่งให้ใบงานเอาจาก `fx_part` / `fxPart` เสมอ** (ดู "เตรียมก่อนรัน") อย่าค้น `partCode='SP-BOARD'`
หรือหยิบ `order by id limit 1` เอง — วันนี้ยังผ่าน แต่พอกฎล็อกยี่ห้อเปิด ชุดนั้นจะพังทั้งที่แอปไม่ได้ผิด
ข้อที่เทียบข้อความซึ่งพิมพ์รหัสอะไหล่ ให้เทียบกับรหัสของตัวที่ส่งจริง (`fx_part_code` ของใบเดียวกัน · ฝั่งเบราว์เซอร์อ่าน
`partCode` จาก id ที่ `fxPart` คืน) ไม่ใช่ `SP-BOARD` ตายตัว — ใบของเครื่อง Huebsch ได้ `SP-BOARD-HB`
· ชุดที่ต้องสร้างอะไหล่ของตัวเอง ใส่ `brand` ให้ตรงกับเครื่องเอง (แบบ `branch-parts-report-test.sh`)

**เทสต์ที่ขึ้นกับเวลาปิดรับปล่อยงานคุมเวลาด้วยแถวใน `AppSetting` ไม่ใช่นาฬิกาเครื่อง** (เริ่มที่ `dispatch-cutoff-test.sh`)
— เวลาปิดรับที่ใช้คือ `value` ของแถวล่าสุด `key='dispatchCutoff'` (ใส่เวลาใด ๆ ได้ทาง SQL ไม่จำกัดแค่ 5 ตัวเลือก ตัวช่วย `SETCUT`)
แล้วต้อง **เรียก `GET /api/settings/dispatch-cutoff` หนึ่งครั้ง** ให้เซิร์ฟเวอร์อ่านสด เพราะมันจำค่าไว้ 30 วินาที — ใส่แถวทาง SQL
แล้วลืมเรียก ผลที่ได้ขึ้นกับว่าอีกชุดเพิ่งอ่านเมื่อไร (ผ่านบ้างไม่ผ่านบ้าง) · เทสต์ต้องผ่านทุกเวลาของวัน ห้ามพึ่งว่า "รันก่อน 16:00"
· ชุดที่ตั้งเวลาไว้ต้องลบแถวที่ตัวเองเพิ่ม (`trap … EXIT`) — **แถวที่ค้างอยู่เปลี่ยนผลของทุกชุดที่รันต่อจากนั้น** โดยไม่มีชุดไหนบอก
· ชุดนี้เปิด `set -eE` กับ trap ERR (เหตุผลเดียวกับ `claim-setup.sh` ด้านล่าง) และตรวจแถวที่ค้างตอนเริ่ม: ถ้ามีจะขึ้น FAIL
บอกรหัสแถวแล้วลบให้ ไม่ใช่ตั้ง 16:00 ทับเงียบ ๆ
- **เวลาปิดรับห่างจากตอนนี้ไม่เกิน ±5 นาที** (`OPEN` = อีก 5 นาที · `CLOSE` = 2 นาทีที่แล้ว) — "งานพรุ่งนี้ก่อน/หลังเวลาปิดรับ" ได้ผลเดียวกันทุกเวลาของวัน
- **ถอยเวลาเริ่มใช้กฎ** (`createdAt` แถวแรก) ไป 30 วันระหว่างรัน แล้วคืนตอนจบ — ไม่งั้นวันที่ migration รัน งานวันนี้ยังไม่อยู่ใต้กฎ (ไม่ล็อกย้อนหลัง)
  ข้อ "งานวันนี้ล็อก" ผ่านหรือไม่ผ่านตามวันที่ฐานนั้นเปิดกฎ · ค่าเดิมจดเป็นแถว `key='dispatchCutoffTestSeedAt'` ในคำสั่งเดียวกับที่ถอย
  (`readCutoff` อ่านเฉพาะ `key='dispatchCutoff'` แถวนี้ไม่มีผลกับแอป) — ถูกฆ่ากลางทาง รอบถัดไปเจอแถวนี้ ขึ้น FAIL แล้วคืนค่าจริงให้
  (ไม่มีแถวจด รอบถัดไปจะจำค่าที่ถอยไว้เป็น "ค่าเดิม" แล้วงานวันนี้ของทุกชุดล็อกตลอดไปโดยไม่มีใครบอก)
- **ตัวกันคร่อมเที่ยงคืน**: เริ่มรันภายใน 10 นาทีก่อน/หลังเที่ยงคืน (เวลาไทย) ชุดนี้รอจนพ้น 00:11 ก่อน เพราะ "วันนี้/พรุ่งนี้" จะเปลี่ยนกลางทาง
  · รอ**ก่อนแตะฐานข้อมูลสักบรรทัด** — ถูกฆ่าระหว่าง `sleep` bash ยังไม่เรียก trap ของที่แก้ไว้ก่อนหน้าจะค้าง · ขยับ offset ±5 นาทีต้องขยับตัวกันนี้ด้วย
- **ชุดที่ต้องปล่อยงานวันนี้ใช้ `confirm-appointment '{"urgent":true}'` หรือ `POST /urgent-release`** (`close-round2` · `pm-photo` ·
  `tech-day` · `stage-speed` · เบราว์เซอร์ `field-flow` · `round2`) — เส้นตายของงานวันนี้ (เมื่อวานตามเวลาปิดรับ) ผ่านไปแล้วเสมอ จึงผ่านได้ทุกเวลาของวัน
  ไม่ว่าฐานจะเปิดกฎเมื่อไร · `stage-speed` ใช้ `urgent-release` แยกหลังคอนเฟิร์ม เพราะข้อนั้นทดสอบทางคอนเฟิร์มแบบคำสั่งเดียว (`moveStage`)
  ติ๊กงานด่วนแล้วจะไปทางทรานแซกชันและมีประวัติแถวที่สอง · ชุดที่ไม่ต้องการวันนี้ปล่อยงานที่ ≥ วันมะรืน (`visitDay(12)` · `visitDay(30)`)
  แล้วค่อยย้ายวันเป็นวันนี้ทาง SQL หลังปล่อย — ห้าม `/dispatch` ใบวันนี้/พรุ่งนี้โดยไม่มีงานด่วน ผ่านตอนเช้า พังหลัง 16:00
- **กล่องงานแอดมินทั่วไป (`status=INBOX` · `/inbox-count` · `/version`) เปลี่ยนตามเวลาด้วย** — ใบรอปล่อยงาน/ส่งช่างตรวจวันนี้ล็อกเสมอ
  พรุ่งนี้ล็อกหลังเวลาปิดรับ และใบที่ล็อกเข้ากล่องแอดมิน (หัวข้อ "เลยเวลาปล่อยงาน") · ชุดที่นับกล่องแอดมิน หรือเช็คว่าใบขั้นปล่อยงาน
  **ไม่อยู่**ในกล่องแอดมิน ใช้วันนัด ≥ วันมะรืน หรือแก้เป็นงานด่วนก่อน — ไม่งั้นผลขึ้นกับว่ารันกี่โมง · กล่องของหัวหน้าภาค/Admin Spare Part ไม่เปลี่ยน

**เทสต์เคลมใช้ `claim-setup.sh` ร่วมกัน** (source อย่างเดียว ไม่อยู่ใน `run-all.sh`) — สาขาแฟรนไชส์ในประกัน เครื่อง Huebsch
ช่างกับ Admin Spare Part ของชุดเอง (`ZCS…` ไม่แตะทีม T001) · `claim_order N` เปิดใบเดินจริงถึงขั้นเข้างาน (อะไหล่จาก `fx_part`)
· `claim_files` · `claim_json` · `claim_skips` · `CLOSE` — รายละเอียดอยู่หัวไฟล์ ถ้าแต่ละชุดคัดลอกกันไปเอง วันหนึ่งจะเพี้ยนไม่เท่ากัน
- **`CLOSE` ใส่เหตุผลไม่ส่งเคลมให้เอง** (เคลมก้อน 5): สาขาทดสอบอยู่ในประกัน ชิ้นใน `PARTS` ที่ไม่อยู่ใน claims ได้ `claimSkips` เหตุผล `DAMAGED_LOST`
  (`claim_skips`) ชุดที่ทดสอบเรื่องอื่นจึงไม่ต้องรู้กติกานี้ · **ชุดที่ทดสอบ "ช่างถอดชิ้นออกจากเคลม" ต้องส่ง `$4` เอง** — `'[]'` = ไม่บอกเหตุผล
  (ไม่งั้นเทสต์ผ่านโดยไม่ได้แตะกติกาเหตุผลเลย) · `PLATE` ตั้งต้นมี `confirmed:true` ที่รุ่นกับ Serial (ไม่มี `verified` แล้ว)
- เก็บกวาดเพิ่มใส่ฟังก์ชัน `claim_extra_cleanup()` (ถูกเรียกก่อนลบของในไฟล์นี้) **อย่าตั้ง `trap … EXIT` ใหม่ทับ** — ของที่ไฟล์นี้สร้างจะค้าง
- ไฟล์นี้เปิด `set -eE` และ trap ERR: คำสั่งที่พังกลางทาง (JSON อ่านไม่ออก · curl ต่อไม่ติด) พิมพ์ `FAIL สคริปต์หยุดกลางทาง …` ก่อนจบ
  — `run-all.sh` นับแค่บรรทัด PASS/FAIL ชุดที่ตายเงียบ ๆ หลังผ่านไปไม่กี่ข้อจะถูกนับว่าผ่าน

**เทสต์เบราว์เซอร์จอกว้าง (≥ 1100) เข้ารายการใบงานจากเมนูข้าง `[aria-label="ใบงานซ่อม"]`** — จอกว้างขนาดนี้เมนูข้างกางค้าง
แท็บล่าง "ใบงาน" ถูกซ่อน หา "ใบงาน" แบบจอมือถือจะรอจนหมดเวลาทั้งที่แอปไม่ได้ผิด (`claim-review-web-test.js` เลือกตามความกว้างจอ)

**ใบที่ปิดแล้ว (`DONE`) ไม่ขึ้นในรายการแท็บเริ่มต้น "ที่ยังค้าง"** ค้นรหัสใบแล้วไม่เจอทั้งที่ใบมีอยู่ — เปิดแท็บ "ปิดแล้ว" ก่อนค้น
(`openOrder(page, code, "ปิดแล้ว")` ใน `claim-review-web-test.js`) · และลิงก์ "เปิดใบงานเต็มใบ ▸" ของกล่องงานตรวจเคลมอยู่ในกล่องรายละเอียดใบงานที่พับไว้
ต้องกด "ดูรายละเอียดใบงาน ▸" ก่อน (ตัวช่วยหา `paneCode` อ่านหัวหน้าตรวจ ใช้ไม่ได้กับหน้าสรุปหลังตัดสินที่ไม่มีหัวนั้น)
